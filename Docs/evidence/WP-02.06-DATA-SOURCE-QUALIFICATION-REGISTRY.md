## Ownership and dependency direction

Source qualification extends `libs/contracts/provider`, the accepted data-platform bounded context. It imports Phase 01 identities but does not add mutable commercial/source policy to canonical business contracts.

```text
reviewed immutable evidence + versioned qualification policy
                              |
canonical SourceIdentity + optional ProviderIdentity path
                              |
provider capability + intended information role/use + coverage
                              |
provider QualificationDecision (immutable/versioned)
                              |
provider QualificationRegistry (exact in-memory lookup/history)
```

The dependency remains one way: `provider -> canonical`. `libs/contracts/canonical` is unchanged and contains no licensing, vendor cost, source trust, provider preference, or qualification lifecycle policy.

Rejected owners:

1. `libs/contracts/canonical`: rejected because qualification is mutable reviewed governance about suitability, not universal canonical business meaning.
2. `libs/marketdata`: rejected because qualification covers filings, macro, reference data, news, events, and datasets as well as market observations.
3. research/event feature packages: rejected because source suitability must be reusable without importing later research behavior.
4. a database/service/remote policy platform: rejected because a deterministic in-process proof is sufficient and persistence was explicitly out of scope.

## Source is not provider

The contract reuses the accepted identities unchanged:

- `canonical.SourceIdentity` is the logical information authority/origin;
- `canonical.ProviderIdentity` is the service/transport that exposes or delivers it.

`QualificationScope.Source` is mandatory. `QualificationScope.ProviderPath` is optional and appears only when transport/path characteristics materially affect suitability. The exact-scope proof registers one logical macro source through two synthetic provider paths: the `SourceIdentity` remains identical while one path is qualified and the other is unqualified because its reviewed storage right prohibits the required use.

The registry never infers source identity from a provider name, URL, endpoint, or display label. A valid provider path must already exist in the accepted WP-02.01 provider registry and statically support the scoped capability.

## Qualification state model

| State | Precise meaning |
| --- | --- |
| `QUALIFIED` | The exact policy requirements are met and the permission for the exact intended use is unconditionally allowed. |
| `CONDITIONALLY_QUALIFIED` | The intended use is allowed only under one or more typed conditions for that use. |
| `UNQUALIFIED` | A hard disqualifier or explicit use prohibition makes the exact scope ineligible. Positive cost/reliability facts cannot override it. |
| `NOT_ASSESSED` | Required qualification evidence or a policy-required reviewed characteristic is missing; the result fails closed and is not equivalent to qualified. |
| `DISABLED` | An explicit Jax governance disablement applies. This remains distinct from a provider that is operationally unavailable. |

State is deterministically derived by `AssessQualification`. A manually supplied state that conflicts with permissions, conditions, or disqualifiers fails validation. Unknown enum values and future decision versions fail closed.

## Authority/source classes

`SourceAuthorityClass` is separate from qualification:

- `OFFICIAL_PRIMARY`;
- `REGULATED_OR_EXCHANGE`;
- `DIRECT_ISSUER`;
- `PROFESSIONAL_SECONDARY`;
- `AGGREGATOR`;
- `COMMUNITY_UNVERIFIED`;
- `MODEL_DERIVED`;
- `OTHER`;
- `UNKNOWN`.

Authority class is a reviewed characteristic, not a score or automatic decision. An official source can still be unqualified because of a path, coverage, provenance, licensing, review, or capability restriction. An aggregator can remain useful for bounded corroboration or investigation while being prohibited from sole canonical factual authority.

## Exact role, capability, use, and coverage scope

Every decision is scoped to:

- exact logical source identity;
- optional exact provider path;
- one accepted WP-02.01 capability;
- one information role;
- one intended use;
- explicit capability-wide, bounded, unsupported, or unknown coverage.

Roles are Jax information roles: authoritative source, primary evidence source, secondary corroboration source, market observation source, reference-data source, filing/document source, macroeconomic authority, news/evidence source, event-detection source, and research-only supplementary source.

Uses are bounded actions: primary evidence, corroboration, investigation trigger, research display, fallback input, and canonical factual assertion. They contain no recommendation, approval, order, execution, broker, or trading authority.

`QualificationPermissions` exposes each use separately. A secondary source fixture explicitly allows corroboration, investigation, and research display while prohibiting primary evidence and independent canonical factual assertion. There is no universal `trusted=true` or provider score.

Coverage uses a small typed dimension/value boundary rather than a global taxonomy. A decision can be capability-wide or bounded by geography, instrument type, venue, series, or dataset. Bounds must be unique and lexically ordered. Unknown and unsupported coverage remain explicit; the representative policy requires known supported coverage.

## Qualification dimensions

The decision preserves dimensions without collapsing them into a weighted number:

| Dimension | Typed semantics |
| --- | --- |
| authority | separate source class above |
| identity certainty | `UNKNOWN`, `LOW`, `MODERATE`, `HIGH`, `VERIFIED` |
| historical reliability | reviewed class plus optional delivery-success, missing-data and correction basis points, outage characteristic, schema-change frequency, and exact observation window |
| availability | unknown, continuously expected, scheduled, or best effort |
| update/latency | unknown, real-time, delayed, periodic, or event-driven |
| provenance quality | unknown, insufficient, source identified, source+revision, or immutable raw+lineage |
| rights | internal processing, persistent storage, derived-data creation, model/research use, redistribution, commercial use, and retention |
| cost | model (`FREE`, `FIXED_SUBSCRIPTION`, `USAGE_BASED`, `TIERED`, `INTERNAL`, `UNKNOWN`) plus bounded class; no prices or account data |
| access stability | unknown, unstable, variable, or stable |
| schema stability | unknown, unstable, managed change, or stable |
| coverage | explicit status/scope/bounds above |

The policy declares minimum identity and long-term reliability classes and whether availability, latency, cost, coverage, stable access, managed schema, persistent storage, derived-data, and research-use facts are required. Unknown required facts fail closed. This is eligibility policy, not provider optimization.

## Reliability is not current health

`HistoricalReliability` describes a reviewed historical observation window. Synthetic proof records delivery success, missing-data incidence, correction incidence, outage character, and schema-change frequency. WP-02.06 does not collect or calculate these from live telemetry.

WP-02.05 `HealthAssessment` answers whether a provider capability can serve reliably now. The qualification registry neither reads nor stores it. Tests evaluate the same qualification while independently varying health across `HEALTHY`, `DEGRADED`, and `UNAVAILABLE`; the qualification decision remains byte-for-byte unchanged.

## Immutable qualification evidence

Every evidence item has a typed purpose and an accepted Phase 01 `canonical.EvidenceRef`. That reference binds:

- canonical Evidence identity/schema;
- exact raw content digest/representation;
- logical evidence source;
- optional provider;
- immutable revision;
- collection and optional source clocks.

Supported qualification evidence kinds are source identity, authority classification, source documentation snapshot, licensing review, historical-reliability snapshot, coverage review, and approved internal review. A mutable URL alone cannot satisfy the contract. Typed reasons cite exact evidence IDs. The policy lists mandatory evidence kinds; missing mandatory evidence yields `NOT_ASSESSED` plus `REQUIRED_QUALIFICATION_EVIDENCE_MISSING`.

## Licensing and usage rights

Rights are reviewed facts, not legal advice or copied vendor terms. Each use right is `ALLOWED`, `RESTRICTED`, `PROHIBITED`, or `UNKNOWN`. Retention is separately indefinite, bounded, session-only, prohibited, or unknown.

The representative policy requires internal processing, persistent storage compatible with WP-02.02 replay/audit retention, derived-data creation for canonical normalization, and model/research use. Unknown or prohibited required rights are hard licensing disqualifiers. A restricted required right is accepted only as `CONDITIONALLY_QUALIFIED` with a typed `USAGE_RESTRICTIONS_APPLY` condition; bounded retention similarly requires `RETENTION_LIMIT_APPLIES`.

Redistribution and commercial-use facts remain explicit even when they are not the intended internal use. No provider contract text, legal conclusion, current price, invoice, billing identifier, account, or secret is recorded.

## Cost boundary

Cost is an explicit model/class characteristic only. The registry contains no prices, invoices, billing IDs, credentials, or selection optimization. A policy can require cost to be known; it cannot make cheap data override licensing, identity, provenance, coverage, or other hard disqualifiers. No sorting or weighted ranking exists.

## Typed conditions and corroboration

Conditions are machine-readable and apply to one exact use:

- independent primary required;
- research display only;
- coverage restricted;
- usage restrictions apply;
- retention limit applies;
- exact freshness policy required.

Conditional permission without a condition, unconditional permission with a condition for the same use, duplicate conditions, and incompatible `RESEARCH_DISPLAY_ONLY` plus `INDEPENDENT_PRIMARY_REQUIRED` conditions fail closed.

The boundary can state that a source may corroborate, trigger investigation, or support research display while it may not act as primary evidence or independently support a canonical factual assertion. It does not implement source triangulation, contradiction resolution, or the later research engine.

## Hard disqualifiers

The closed model includes:

- unknown/invalid source identity;
- invalid or missing provenance;
- licensing prohibition for the intended use;
- capability/role/use mismatch;
- insufficient identity certainty;
- unknown/unsupported coverage;
- model-derived authoritative claim;
- required qualification evidence missing;
- insufficient historical reliability;
- unstable access or schema characteristics when policy requires stability;
- explicit intended-use prohibition;
- conflicting/missing conditions;
- qualification expiry;
- review overdue;
- explicit source disablement.

Hard disqualifiers are de-duplicated and sorted deterministically. The proof sets historical reliability to `STRONG` and cost to `FREE/NEGLIGIBLE` while prohibiting required storage; the result remains `UNQUALIFIED`.

## AI/model-derived sources

Model-derived material is classified explicitly with `MODEL_DERIVED` authority. Accepted canonical Evidence V2 already requires provenance for model output. WP-02.06 additionally prohibits model-derived material from self-qualifying for authoritative/primary/canonical-factual use, regardless of model confidence. It may be assessed for a bounded supplementary, corroborating, or investigation role under separate evidence and policy, but no inference or model call occurs here.

## Policy, assessor, effective time, review, and history

Each immutable `QualificationDecision` records:

- decision contract version and `qlf_` identity;
- decision-version identity;
- exact typed scope;
- exact policy `ComponentIdentity` with `jax.policy.qualification` version;
- exact assessor `ComponentIdentity` with `jax.assessment.qualification` version;
- evidence, dimensions, permissions, conditions, reasons, state, and disqualifiers;
- `assessed_at`, `effective_from`, optional `effective_to`, required bounded `review_due_at`, and optional superseded decision ID.

There is no implicit clock. `LookupAt` requires an explicit UTC time. Review is overdue at `T >= review_due_at`; expiry applies at `T >= effective_to`. Both produce an effective `UNQUALIFIED` result with a visible temporal disqualifier, without modifying the stored historical decision.

Changed evidence, policy, rights, or result creates a new decision. A successor explicitly names the prior decision and advances effective time. The registry stores both; before the successor time lookup returns the old decision, and at/after it returns the new decision. The test changes the exact qualification policy version between the two records. The prior record is not rewritten.

## Registry semantics

`QualificationRegistry` is a deterministic in-memory catalogue with contract version `jax.source_qualification_registry/v1`.

It provides:

- registration of exact qualification policy versions;
- validated immutable decision registration;
- exact lookup by source/provider-path/capability/role/use/coverage at explicit historical time;
- ordered exact-scope history;
- rejection of duplicate identities, overlapping/ambiguous declarations, branched supersession, source-identity kind conflicts, unknown providers, unsupported path capabilities, invalid intervals, and unsupported versions;
- defensive copies so callers cannot mutate registered meaning;
- distinct unknown, not-yet-effective, explicitly unqualified, expired, review-overdue, disabled, and qualified results.

Registration rejects ambiguity before mutation. Lookup also detects ambiguous stored history as corruption and fails closed. The registry has no database, global singleton, discovery, plugin loading, remote configuration, scheduler, provider call, dynamic telemetry, or source selection.

## Health, freshness, normalization quality, and qualification remain independent

The valid Phase 02 dimensions are:

```text
source qualification:           QUALIFIED
provider/capability health:      DEGRADED
exact datum temporal state:      FRESH
normalization quality:           CANONICAL_VALIDATED
```

WP-02.06 contains no health or datum-freshness field. It may record a typed condition requiring an exact freshness policy, but actual datum age/TTL/LKG evaluation remains WP-02.04. It cannot upgrade stale data, repair invalid canonical output, or turn a healthy provider into a qualified source. Tests prove `HEALTHY + UNQUALIFIED`, `HEALTHY + QUALIFIED`, `UNAVAILABLE + QUALIFIED`, and `DEGRADED + QUALIFIED` remain representable.

## Source-selection boundary

The registry answers whether exact source/path X is eligible for bounded use Y at historical time T. It does not:

- rank all sources/providers;
- compute a trust score;
- choose the cheapest, freshest, healthiest, or most authoritative provider;
- fail over across vendors;
- call a provider or model;
- create research conclusions or trading recommendations.

A later reviewed orchestrator may combine capability support, qualification, health, datum freshness, cost constraints, and research context. That work is not started.

## Representative executable proof

Focused tests demonstrate:

1. a synthetic official macro authority is qualified for canonical factual assertion;
2. a professional secondary news source is qualified for corroboration while primary/canonical authority remains prohibited;
3. a provider path is unqualified because persistent storage is prohibited;
4. current health changes do not change qualification;
5. datum freshness changes do not change qualification;
6. strong reliability and negligible cost cannot override a licensing disqualifier;
7. lookup is exact across source, provider path, capability, role, use, coverage, and time;
8. duplicate and ambiguous declarations fail, and corrupted ambiguous lookup fails closed;
9. old and new decisions under different policy versions reconstruct correctly at historical T;
10. missing evidence yields fail-closed `NOT_ASSESSED`;
11. no network, model, database, ambient clock, or randomness participates;
12. the same logical source through two providers retains one SourceIdentity while path decisions differ;
13. strict JSON rejects unknown/duplicate/null/future-version/trailing/invalid-UTF8 input.

## Phase 02 exit-gate proof

`TestPhase02ExitChainUsesCanonicalProviderNeutralResearchRepresentation` demonstrates the required chain with synthetic data:

```text
WP-02.01 synthetic ProviderDefinition + macro.observation capability
        |
WP-02.05 OperationalExecutor succeeds with exact provider bytes + HEALTHY assessment
        |
WP-02.02 PersistRawPayload stores and retrieves the exact bytes/SHA-256 provenance
        |
WP-02.03 exact provider/raw-schema normalizer emits canonical Observation V2
        |
canonical validation + immutable output + raw EvidenceRef/Provenance
        |
WP-02.04 explicit-time freshness evaluation returns FRESH
        |
WP-02.05 HealthAssessment remains HEALTHY
        |
WP-02.06 exact source/provider-path qualification returns QUALIFIED
        |
research-facing projection accepts canonical.Observation only
```

The proof registers a second synthetic adapter with a different ProviderIdentity and raw schema but the same WP-02.01 capability and canonical Observation V2 destination. The downstream projection signature and result contain only canonical subject, metric, value, unit, and observation time; provider DTOs, methods, endpoints, and identity do not leak into research logic. Provider identity remains available separately in raw/canonical provenance.

This demonstrates the Phase 02 exit condition without building a Phase 03 provider integration or Phase 03 research consumer. Codex does not issue the phase-gate decision.
