## Raw payload identity and reference design

`RawPayloadRef` is versioned as `jax.provider_raw_payload_ref/v1` and contains no raw bytes. It binds:

- `RawPayloadID` with the `rpa_` prefix: one stable Jax raw-payload acquisition identity;
- accepted Phase 01 `ContentIdentity` using `raw_bytes` and SHA-256;
- accepted `ProviderIdentity`;
- the declared WP-02.01 `CapabilityID`;
- the exact provider-raw boundary, format, provider schema/version, and actual media type;
- explicit byte-capture/content-coding/character-encoding metadata;
- optional logical `SourceIdentity`, never fabricated;
- optional immutable provider/source `RevisionIdentity` when available;
- UTC receipt-completion time;
- exact byte count;
- explicit replay/audit retention policy identity and redistribution boundary.

`RawPayloadID` is deliberately not derived from the digest. Content identity answers "which bytes?" while `RawPayloadID` answers "which acquisition?" This separation preserves two receipts of identical content as distinct historical observations.

The `rpl_` serialized namespace remains reserved for accepted Phase 01 `ReplayManifestID`. `rpa_` was selected only after a repository-wide prefix inventory confirmed it was unused. Distinct global serialized namespaces are required even though Go uses distinct types: identifiers cross JSON, persistence, audit, replay, and provenance boundaries where their static Go type may no longer be present. The focused contract regression proves that replay accepts `rpl_` and rejects `rpa_`, raw payloads accept `rpa_` and reject `rpl_`, and `rpa_` does not equal the nearby accepted canonical/provider-related prefixes.

`RawPayloadDescriptor` combines the immutable reference with a current logical `RawPayloadLocation`. A descriptor is a retrieval result, not a second content identity.

## Authoritative-byte and transport semantics

The authoritative forensic representation is exactly the byte slice supplied to `PersistRawPayload` at the declared adapter capture point. `canonical.RawContentIdentity` hashes those bytes directly. The package does not parse and reserialize JSON, normalize whitespace or line endings, convert timestamps/numbers, reorder keys, decode text, or otherwise transform the bytes before hashing.

The default capture form is the complete entity/body bytes after protocol transfer framing has been removed and before provider-specific parsing, character decoding, or normalization. HTTP chunk framing is therefore not part of the entity body. Content coding is explicit:

- `IDENTITY`: no content coding changed the retained bytes;
- `ENCODED`: retained bytes still use the named coding, such as gzip;
- `DECODED`: transport tooling decoded the named coding before capture, and the digest identifies the decoded entity bytes actually presented to persistence.

If both encoded and decoded representations are materially required, each is persisted as a separate `RawPayloadRef` with its own digest and acquisition identity. `CONTENT_DECODED_FROM` records their relationship; they are never silently conflated.

Multipart responses are retained as one complete entity by default. A separately retained part uses `MULTIPART_PART` and must point to its containing payload through `MULTIPART_PART_OF`. Binary bodies are ordinary byte sequences under the WP-02.01 `BINARY` format. Character encoding is informational metadata only and never causes transcoding.

The `Complete` acquisition assertion plus non-empty byte requirement is fail-closed protection against known incomplete/truncated capture. This package does not build an HTTP stack or infer completeness from transport headers.

## Provider, source, capability, and schema relationship

`PersistRawPayload` resolves the complete accepted `ProviderIdentity` through the WP-02.01 registry, requires the named capability to be declared and statically `SUPPORTED`, and checks the received provider-raw boundary, raw format, and provider schema identity against the declaration. If the capability constrains a media type, the actual base media type must match; valid parameters such as `charset=utf-8` remain representable.

Provider and source retain their accepted distinction:

- provider is the service/transport that supplied the bytes and is always known for an accepted raw reference;
- source is the logical authority/publisher/exchange/regulator/dataset and remains optional until genuinely known.

No source identity is inferred from the provider name. A source-attributed reference with an immutable revision can use `AsEvidenceRef` to carry the exact raw `ContentIdentity`, provider, source, revision, and receipt time into the accepted Phase 01 immutable evidence vocabulary. The bridge creates no canonical Evidence record and performs no normalization. It fails if source or revision is absent.

## Raw versus canonical boundary

`RawPayloadRef.Raw.Boundary` must remain `PROVIDER_RAW`. Raw metadata may describe provider/capability/schema/content/acquisition/retention, but neither the bytes nor the reference are canonical domain records. JSON that resembles an Event, Evidence, or Observation remains provider input until an explicit future WP-02.03 normalizer validates and produces a canonical contract with provenance.

No provider-specific mapping, normalization transform, schema translation, normalization orchestration, or canonical record generation exists in this package.

## Content hashing and integrity

The implementation reuses Phase 01 `canonical.RawContentIdentity`, `ContentDigest.VerifyBytes`, and SHA-256. It adds no hash algorithm or digest vocabulary.

- same bytes produce the same content digest;
- any byte change produces a different digest;
- retrieval verifies both byte count and digest;
- digest failure returns typed `digest_mismatch` and never yields bytes as verified;
- raw reference JSON contains identity/metadata only, never the raw bytes.

A digest proves byte identity, not provider truth, completeness beyond the adapter assertion, licence permission, source quality, or freshness.

## Persistence abstraction and atomicity

`RawPayloadStore` is deliberately small:

```go
Put(context.Context, RawPayloadRef, []byte) (RawPayloadLocation, error)
Get(context.Context, RawPayloadRef) ([]byte, error)
```

`PersistRawPayload` is the acceptance operation:

1. validate completeness, retention, provider, capability, raw schema, media type, capture metadata, and reference metadata;
2. hash the exact bytes and derive byte count;
3. call immutable `Put`;
4. retrieve by the exact typed reference;
5. verify size, SHA-256, and equality with the supplied bytes;
6. validate the logical location;
7. return the accepted descriptor.

Any failure returns a zero descriptor. A successful reference is not published before successful persistence and read-back verification.

The port contract requires a backend `Put` to expose either the complete bytes or an error and prohibits replacement under an existing acquisition identity. A future metadata/blob split must commit or recover so metadata is not published before blob verification. An unreferenced blob left after failed verification is an acceptable recoverable orphan; silently publishing a missing/corrupt reference is not. No distributed transaction is required.

`MemoryRawPayloadStore` is a concurrency-safe deterministic proof, not a durable runtime backend. One lock atomically installs the acquisition record and content blob after validation.

## Storage location versus identity

`RawPayloadLocation` is a logical store version plus opaque logical key. It intentionally contains no filesystem path, URL, bucket name, database row ID, endpoint, or credential. Physical adapters resolve and may migrate placement without changing `RawPayloadRef`.

The in-memory proof uses `sha256/<digest>` as a content-level locator, but retrieval still requires the complete typed reference and verifies content. The locator cannot substitute for `RawPayloadID` or `ContentIdentity`, and it is not introduced into canonical provenance.

This abstraction permits future local filesystem/object-store development, durable object storage, or database metadata plus external blobs without changing downstream domain contracts.

## Immutability, idempotency, and deduplication

- Same acquisition ID plus the exact same immutable reference and bytes is idempotent.
- Same acquisition ID with different content or metadata returns `duplicate_identity_conflict`; no overwrite occurs.
- Same content under a different acquisition ID creates a distinct acquisition record and may reuse one content blob.
- New/different bytes require a new content identity and normally a new acquisition identity/revision.
- Store reads and writes use defensive byte/pointer copies in the in-memory proof.

Example: identical filing bytes received at 10:00 and 10:05 have one SHA-256/blob but two `rpa_` identities and receipt timestamps. Acquisition history is not lost to content deduplication.

## Retention and redistribution policy

An accepted `RawPayloadRef` requires `REPLAY_AUDIT_REQUIRED` plus a namespaced policy version. This is retention intent, not an arbitrary calendar duration: the bytes must remain available while material provenance/audit/replay references depend on them. A future backend may not silently treat them as disposable cache entries.

Temporary transport buffers are non-authoritative and do not receive an accepted raw reference or become eligible for canonical processing. Lifecycle deletion, garbage collection, archival, TTL, last-known-good, and scheduled cleanup are not implemented.

Redistribution intent is explicit as `NOT_AUTHORIZED`, `RESTRICTED`, or `AUTHORIZED`. The field prevents an assumption that stored provider bytes are freely redistributable. It does not encode vendor licence text, score providers, qualify sources, or implement enforcement. Provider-specific licensing/cost/trust decisions remain WP-02.06.

## Sensitive-data boundary

Raw request authentication material is not part of any contract. There are no fields for headers, Authorization, API keys, cookies, credentials, secret locations, environment variables, endpoints, or request configuration. Strict JSON decoding rejects attempted unknown fields such as `authorization`.

Legitimate provider response bodies are preserved exactly even when sensitive, subject to storage access controls in a future backend. The package does not log payload bytes or credential material; typed error detail is bounded to failure class and identity.

## Provenance and replay integration

The exact raw content identity can become the accepted `EvidenceRef.Content` without rehashing or relabeling. `AsEvidenceRef` proves the bridge when source and revision are known, and tests prove the resulting `EvidenceRef` is valid as a Phase 01 `LineageInput` with a deterministic input fingerprint.

Historical replay can therefore retrieve bytes through the raw reference, verify exact size/SHA-256, and use the same immutable evidence content identity that downstream provenance records used. WP-02.02 does not implement an audit event store, replay engine, reconstruction service, or provenance graph.

## Failure and observability semantics

`RawPayloadError` exposes deterministic typed codes without payload contents:

- unsupported reference version;
- invalid reference;
- unknown/mismatched provider;
- undeclared or unavailable capability;
- raw schema/boundary/format mismatch;
- unsupported media type;
- invalid retention declaration;
- incomplete/empty payload;
- persistence failure;
- duplicate identity conflict;
- missing retrieval;
- byte-count mismatch;
- digest mismatch.

Registry errors remain available through error unwrapping. Persistence failure cannot masquerade as an acquisition suitable for normalization: `PersistRawPayload` returns no accepted descriptor. No retry, backoff, health collector, metrics platform, or raw-content logging is added.

## Fincept and mature-pattern assessment

The committed Phase 02 reference notes were used at concept level. Fincept DataHub and normalization references support explicit raw/normalized separation, persistence, and provider ownership; dormant connector inventory is not treated as production capability. No Fincept source, schema, topology, or dependency is copied.

Mature content-addressed-storage principles used here are deliberately small: immutable digest-addressed blobs, separate acquisition metadata, verified reads, idempotent puts, and logical locators. Go's standard library plus the accepted Phase 01 SHA-256 contracts are sufficient. A CAS framework, repository framework, event store, distributed transaction system, and new cryptographic dependency were rejected as unnecessary.

## Rejected alternatives

1. Store raw bytes in `libs/contracts/canonical`: rejected because canonical owns normalized domain/provenance meaning, not provider payload storage.
2. Extend `event_raw` or World Monitor JSONB now: rejected because both reserialize data, have feature-specific identity, and overwrite conflicts; changing them would be a runtime/migration project.
3. Use a URL, path, object key, or row ID as payload identity: rejected because locations move and do not prove content.
4. Make `RawPayloadID` content-derived: rejected because repeated acquisition history would collapse.
5. Store one blob per acquisition without content deduplication: valid but wasteful; the reference model permits content dedup while preserving acquisition records.
6. Parse/canonicalize JSON before hashing: rejected because it destroys forensic byte identity.
7. Always hash HTTP wire/chunk bytes: rejected because adapters normally consume entity bodies and protocol framing is not stable application content. Content coding state makes the actual capture representation explicit, and dual representations can be related when needed.
8. Persist request headers/authentication: rejected because credentials are not provider response evidence.
9. Add PostgreSQL/object-store/filesystem production persistence or a migration: rejected because the port and in-memory proof satisfy this package without choosing deployment infrastructure.
10. Add retention durations, deletion jobs, TTL/freshness, retries, health, or source scoring: rejected as later-package scope.

## Validation and negative-path evidence

Deterministic tests cover:

- exact bytes, line endings, and whitespace producing exact/different SHA-256 identities;
- reference/capture/retention validation and unsupported version rejection;
- distinct `rpa_` raw-payload and accepted `rpl_` replay-manifest identity namespaces, plus a bounded nearby-prefix collision guard;
- provider identity mismatch, unknown provider, undeclared/unavailable capability;
- provider raw schema and media-type mismatch;
- entity/coding and multipart relationship rules;
- persist/retrieve/verify and defensive byte copies;
- tampered/missing/truncated stored content;
- same acquisition/same content idempotency;
- same acquisition/different content conflict;
- same content/different acquisition history plus one deduplicated blob;
- write failure returning no descriptor;
- strict stable JSON, unknown secret-bearing fields, duplicates, nulls, trailing data, and invalid UTF-8;
- `EvidenceRef`/`LineageInput` provenance integration and refusal to fabricate a source.
