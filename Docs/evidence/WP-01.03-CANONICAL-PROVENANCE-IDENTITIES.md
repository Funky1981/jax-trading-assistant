## Provenance primitives

| Primitive | Semantics |
| --- | --- |
| `ContentDigest` | Algorithm-qualified, lower-case hexadecimal cryptographic digest. V1 supports SHA-256 only and fails closed for empty, unsupported, malformed, wrong-length, or non-canonical encodings. |
| `ContentIdentity` | Says whether the digest covers exact `raw_bytes` or the versioned `canonical_json` representation. |
| `SourceIdentity` | Stable `src_` identity for the logical publisher, regulator, exchange, issuer, dataset, or internal source. Provider/model kinds are structurally rejected here. |
| `ProviderIdentity` | Separate stable `pvd_` transport/service identity with an explicit lower-case namespace and optional provider external identity. |
| `RevisionIdentity` | Namespaced immutable source revision, accession, response, vintage, or record revision identity. |
| `VersionIdentity` | Namespaced version value such as `semver`, `git.commit`, `provider.model_id`, `jax.prompt`, or `jax.policy`; it is not a record revision or contract schema version. |
| `ComponentIdentity` | Stable `cmp_` identity, typed class, name, namespaced version, optional exact content identity/provider. Supported classes cover method, algorithm, model, prompt, policy, tool, mapping, normalizer, resolver, validator, software build, and configuration. |
| `EvidenceRef` | Versioned immutable reference to canonical Evidence plus exact forensic raw content, logical source, optional provider, source revision, and observed/published/collected clock roles. |
| `ImmutableContractRef` | Contract kind/ID/schema plus exact record revision and the content identity of the canonical serialized record. |
| `DatasetSnapshotRef` | Logical dataset identity plus existing registry/provider identity, schema version, exact snapshot ID/revision/content, optional as-of time, and collection time. Machine paths are excluded. |
| `LineageInput` | Closed union of immutable canonical contract, EvidenceRef, or DatasetSnapshotRef input. It never embeds a full input object. |
| `Provenance` | Versioned `pvn_` identity containing ordered immutable inputs, verified input fingerprint, primary producer, and materially relevant supporting components. |

The vocabulary deliberately keeps these identities separate:

- contract schema version;
- record/source revision;
- content digest and representation;
- component/model/prompt/policy/tool/build version;
- provenance identity and input fingerprint;
- future replay identity.

## Immutable EvidenceRef semantics

`EvidenceRef` is not a second Evidence record. It contains no title, summary, links, value, or complete payload. It answers which canonical Evidence identity/version was used and binds it to:

- the exact forensic raw content bytes through `ContentIdentity`;
- the logical `SourceIdentity`;
- the separately identified supplying `ProviderIdentity`, when present;
- a required source/provider revision identity;
- acquisition clock roles needed to distinguish what was knowable at decision time.

An EvidenceRef therefore does not depend on a mutable row, URL, current response, runtime path, model output, or log. A URL may remain a boundary locator on Evidence, but it never satisfies immutable identity. EvidenceRef requires `raw_bytes`, so it cannot mislabel reparsed/normalized JSON as the provider response. `ContentDigest.VerifyBytes` deterministically proves whether later bytes are the same exact bytes and returns a typed `DigestMismatchError` on tampering.

Evidence V2 cross-checks that its immutable reference identifies the same Evidence ID/schema, logical source, publication time, and collection time. Downstream lineage may use:

- `EvidenceRef` when the exact forensic/source evidence bytes are the relevant input; or
- `ImmutableContractRef` when the exact complete canonical Evidence record representation is the relevant input.

That distinction prevents a normalized record revision from being mistaken for unchanged raw evidence.

## Hash and deterministic serialization rules

### Raw external evidence

`DigestBytes` and `RawContentIdentity` hash the supplied byte sequence exactly with SHA-256. There is no newline conversion, character decoding, decompression, JSON parsing, key sorting, whitespace rewriting, or semantic normalization. A future adapter must supply the actual immutable received/stored bytes and retain any transport decoding policy outside this identity.

Arbitrary provider JSON is treated as raw bytes. Jax does not assume that a provider's JSON key order, whitespace, number formatting, or regenerated response is stable.

### Jax-owned canonical values

`CanonicalContractBytes` first calls the existing strict `EncodeJSON`, then wraps the record in this fixed envelope:

```json
{
  "canonicalization": "jax.canonical-contract-json/v1",
  "contract_kind": "<kind>",
  "contract_version": "<schema>",
  "content": { "<validated canonical contract>": "..." }
}
```

The actual output is compact JSON. Determinism follows from bounded package rules:

- canonical contracts contain no maps;
- struct field order is fixed and slice order is meaningful;
- required times are UTC and `time.Time` JSON uses RFC 3339 Nano;
- finite Go numbers use `encoding/json`'s locale-independent shortest round-trip representation;
- NaN and infinity fail validation;
- the envelope binds kind, schema, and canonicalization version;
- no file path, logger field, pointer address, process state, or Go memory representation is hashed.

`CanonicalContractContentIdentity` and `VerifyCanonicalContract` compute and verify this representation. Tests prove repeated equivalent values have identical bytes/digests and a material value change changes verification.

### Input fingerprint

`ComputeInputFingerprint` validates and hashes the compact JSON envelope `jax.lineage-inputs/v1` over the ordered `LineageInput` references. The input order is semantic. `Provenance.Validate` recomputes the fingerprint, rejects a mismatch, and independently rejects duplicate exact inputs and self-referential output lineage.

## Source and provider identity

Source and provider are deliberately not aliases:

- source is the logical information authority or origin, such as SEC EDGAR, Reuters, an exchange, a FRED dataset, or an internal canonical source;
- provider is the transport/service that delivered it, such as a provider API, aggregator, database snapshot service, or internal collector.

Both have canonical Jax IDs with different prefixes (`src_` and `pvd_`). Provider external/request identities remain explicitly namespaced and cannot masquerade as either canonical ID. A source classified as `provider` or `model` is rejected in new immutable identities, closing the ambiguity retained only for WP-01.02 V1 compatibility.

## Component, model, prompt, policy, tool, and build identity

`ComponentIdentity` adds the precision intentionally absent from the compact V1 `ComponentRef`:

- a stable Jax component ID;
- an explicit producer class;
- a human/technical name;
- a required namespaced version identity;
- an optional exact content identity for implementation/config bytes;
- an optional provider identity.

Model components require a provider identity. The exact provider model ID belongs in the model's `VersionIdentity`; the model family/name alone is insufficient. Prompt components require a content digest as well as a prompt version. Policy, validator, resolver, mapping, normalizer, tool, configuration, and software-build components can carry exact content/build digests when material.

A `Provenance` record separates the primary producer from supporting components. This supports an AI-derived output identifying provider, exact model ID, prompt identity/hash, output canonical contract version, policy/validator/resolver/tool versions, and materially relevant build/config identity without storing credentials, invoking inference, or accepting model output without deterministic validation.

## Dataset snapshot identity

`DatasetSnapshotRef` expresses the required point-in-time identity:

```text
logical DatasetIdentity
+ external registry/provider identity
+ dataset schema VersionIdentity
+ exact DatasetSnapshotID
+ namespaced revision/vintage
+ ContentIdentity
+ as-of/collection clocks
```

The content identity, not a machine-local file path, is portable. A later snapshot can retain the same logical dataset while changing snapshot ID, revision, as-of time, and content digest. Tests prove that a later revision produces a distinct lineage fingerprint.

## Contract compatibility decision

WP-01.02 explicitly stated that strict V1 decoding makes field additions a new-version decision. WP-01.03 therefore does not silently redefine serialized V1.

- `jax.evidence/v2`, `jax.observation/v2`, `jax.research_run/v2`, `jax.quant_result/v2`, and `jax.recommendation/v2` are introduced for provenance-bearing forms.
- The existing Go structs host both explicit versions to avoid a competing second family. V2 fields use `omitempty`, but V1 validation rejects them if populated.
- Existing V1 encodings and the accepted `recommendation_v1.json` fixture remain byte-for-byte unchanged and readable.
- Empty, future, or unsupported versions fail closed.
- Issuer, Instrument, and Event do not receive speculative V2 versions.

This is an additive contract version, not a production API or persistence migration. Future adapters must select V1 versus V2 explicitly and cannot silently reinterpret old data.

## Validation and negative-path evidence

Validation is deterministic, returns `*ValidationError` for malformed identities/contracts, and returns `*DigestMismatchError` for verified content changes. Tests cover:

- empty provenance identity and malformed canonical IDs;
- unsupported digest algorithm, wrong digest length, malformed hex, and non-canonical encoding;
- immutable-content hash mismatch;
- empty logical source and invalid provider namespace;
- structural source/provider confusion;
- missing component version, model provider, and prompt content hash;
- duplicate immutable inputs and self-referential lineage;
- incompatible contract/version references;
- EvidenceRef without a content identity;
- provenance input-fingerprint mismatch;
- stable canonical serialization and same-input digest;
- changed raw/canonical input producing a different identity;
- V1 rejection of V2 provenance fields;
- strict V2 JSON round trips for Evidence, Observation, ResearchRun, QuantResult, and Recommendation;
- dataset revision distinction and AI provenance composition.

Failures never produce a successful digest verification or validated provenance record.

## Rejected alternatives

1. Add a second provenance/domain package: rejected because `libs/contracts/canonical` is the accepted sole owner.
2. Mutate V1 field semantics: rejected because WP-01.02 explicitly required a new contract version for strict serialized additions.
3. Put every identity/version in one giant provenance struct: rejected in favor of small composable source, provider, revision, content, component, dataset, input, and provenance values.
4. Treat URL, row ID, file path, current provider response, log, or model output as immutable identity: rejected because none proves exact decision-time content.
5. Hash Go object memory or arbitrary reparsed provider JSON: rejected because representation is unstable/ambiguous.
6. Generalize a full RFC/JCS/provenance framework or add a dependency: rejected because bounded Go structs, `encoding/json`, and standard-library SHA-256 satisfy current consumers.
7. Introduce BLAKE/custom crypto or multiple algorithms speculatively: rejected; SHA-256 matches Jax's strong existing foundations and unsupported algorithms fail closed.
8. Make source and provider synonyms: rejected because logical authority and transport can differ.
9. Store recursive full inputs or build a lineage graph database: rejected as unnecessary and beyond the package boundary.
10. Implement audit/replay or persistence now: rejected as WP-01.04/Phase 02 scope.
