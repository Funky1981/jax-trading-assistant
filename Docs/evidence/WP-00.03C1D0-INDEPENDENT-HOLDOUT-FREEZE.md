# WP-00.03C1D0 independent holdout freeze

Created: 2026-08-12

## Scope and independence

This package freezes data and validation design only. It does not implement a deterministic guard, change the issuer schema or policy, run model inference, contact a model provider, mutate a database, or mutate trading state.

The 48-case generalization holdout was constructed and frozen before reviewing detailed C1C response artifacts or the WP-00.03 forensic report for `issuer-diag-013`, `issuer-diag-014`, `issuer-diag-021`, `issuer-diag-039`, `issuer-diag-040`, `issuer-diag-041`, or `issuer-diag-042`. Construction used only the canonical `EventInput` structure, frozen v4 prompt policy, adjudicated benchmark structure, manifest/fingerprint format, bounded exposure definitions, and deterministic resolver rules needed to assign `expected_resolution_status`.

The boundary challenge set was constructed only after the generalization holdout had been frozen. Neither dataset may be modified after model outputs are observed; a changed corpus requires a new version and identity.

## Adjudication methodology

Each case is adjudicated from receipt-time evidence under `ai-shadow-prompt-v4-issuer-resolution` and `event-asset-resolution-v1`:

- `DIRECT`: receipt-time evidence explicitly and unambiguously identifies one traded issuer that is causally affected. An issuer absent from the deterministic resolver remains `DIRECT`; expected resolution is then `unresolved`.
- `PROXY`: no directly identified traded issuer exists, but exactly one bounded principal exposure is defensible.
- `UNRESOLVED`: neither one causal direct issuer nor one bounded principal exposure can be justified. Multiple equally causal issuers are also unresolved.

Materiality is not an issuer-recognition gate. Both datasets include low- or weak-relevance but genuinely causal `DIRECT` events so a reject-most/high-relevance-only implementation cannot achieve acceptable recall merely by abstaining.

Expected deterministic resolution is checked offline against the unchanged frozen ruleset. Alphabet/Google cases are deliberately `DIRECT` at issuer recognition but `ambiguous` at deterministic resolution because the ruleset does not silently choose a listed share class.

No case required an adjudication guess. Ambiguous receipt-time evidence was redesigned to make the policy outcome explicit or labelled `UNRESOLVED`. The only retained policy-level ambiguity is the already-defined Alphabet share-class resolution result, recorded explicitly as `expected_resolution_status: ambiguous`.

## Leakage and consistency validation

`internal/modules/aishadow/holdout_datasets_test.go` performs deterministic offline checks for:

- strict JSON decoding and canonical input-field completeness;
- version, prompt, output-contract, label, policy, count, and distribution identities;
- manifest file SHA-256 and semantic fingerprint;
- input-lock file SHA-256, semantic fingerprint, per-case order, and per-input fingerprint;
- label shape and bounded exposure consistency;
- `expected_resolution_status` agreement with the unchanged resolver policy;
- duplicate case IDs, exact canonical input duplicates, and normalized wording duplicates across the original frozen 48 and both new sets;
- token-set near-copy comparison across datasets with a rejection threshold of 0.72.

The maximum cross-dataset token-set similarity observed was 0.357 (`issuer-generalization-v1-010` versus `issuer-boundary-v1-013`), below the 0.72 near-copy threshold. No exact or normalized duplicates were found.

Zero model inference was run. No Luna, Terra, Sol, DeepSeek, Ministral, Ollama, OpenAI, or other hosted/local model request was made. No provider preflight or provider identity request was made. No database or trading mutation occurred.
