## Ownership and dependency direction

The provider registry and capability vocabulary live in `libs/contracts/provider`, beside but not inside the sole canonical domain package. This is the smallest shared owner because both current Go runtimes can depend on the contract without depending on a provider implementation or reversing ADR-0012 direction.

```text
provider clients / World Monitor / datasets / event feeds / test doubles
                               |
               future feature-owned provider adapters
                               |
           libs/contracts/provider (static declarations)
                               |
       canonical identities and exact destination schema refs
                               |
              libs/contracts/canonical (domain owner)
```

The dependency is one way: `provider -> canonical`. The canonical package does not import the provider package. `libs/marketdata` was rejected as the owner because it is an active market-price client with concrete vendor SDKs, secrets-bearing runtime configuration, caching, fallback, health calls, and a method-shaped interface. It is one future adopter, not the owner of news, filings, macro, calendar, and reference-data capability meaning.

A new top-level module was also rejected. `libs/contracts` already provides the shared, versioned contract boundary, and adding another Go module would create replace/workspace/version overhead without a consumer need.

## Provider identity semantics

`ProviderDefinition.Identity` reuses the accepted Phase 01 `canonical.ProviderIdentity` exactly:

- stable Jax provider IDs use the `pvd_` prefix;
- the lower-case namespace identifies provider/service identity independently from display text;
- optional `ExternalID` remains a provider/registry identity, not the Jax identity;
- complete typed identity is required for lookup;
- the same Jax ID with a different namespace/external identity fails with `provider_identity_mismatch`;
- duplicate provider IDs fail with `duplicate_provider`;
- two Jax IDs claiming one provider namespace fail with `ambiguous_provider`.

Provider identity is not a URL, display name, dataset, canonical SourceIdentity, credential, provider method, or environment configuration instance. One provider has one stable Jax identity; direct SDK versus bridge transport is an adapter/configuration concern unless evidence later proves they are distinct supplying services.

Logical publisher/source identity remains `canonical.SourceIdentity`. Future raw evidence can therefore retain the accepted chain:

```text
provider capability -> exact raw bytes -> EvidenceRef.Provider
                                      -> EvidenceRef.Source
                                      -> normalization provenance
                                      -> canonical record
```

No `SourceIdentity`, `ContentIdentity`, `EvidenceRef`, provider identity, or lineage type was recreated.

## Registry contract

`provider.Registry` is a deterministic in-memory catalogue with contract version `jax.provider_registry/v1`.

It provides:

- validated registration of `ProviderDefinition` values;
- lookup using complete typed `canonical.ProviderIdentity`;
- capability lookup by typed Jax `CapabilityID`;
- lexically deterministic provider listing;
- defensive copies on register/lookup/list so callers cannot mutate registered meaning;
- typed `RegistryError` codes for unsupported registry version, invalid definition, duplicate provider, ambiguous provider, invalid/unknown provider, identity mismatch, and unknown capability.

Unknown and known-but-unavailable are different outcomes. Unknown provider/capability lookup returns a typed error. A known capability with static `UNAVAILABLE` support returns successfully and exposes that state. Operator-visible failure never appears as successful registration; invalid registration leaves the registry unchanged.

The registry has no service discovery, distributed coordination, database, singleton/global, endpoint resolver, factory, client lifecycle, health collector, or configuration loader.

## Capability vocabulary

Capability IDs describe what information Jax can request, never concrete methods such as `GetCandles` or vendor endpoints.

| Capability ID | Category | Normative canonical destination |
| --- | --- | --- |
| `reference.instrument` | `reference_data` | Instrument V1, Issuer V1 |
| `market.quote` | `market_data` | Observation V2 |
| `market.bars` | `market_data` | Observation V2 |
| `market.trades` | `market_data` | Observation V2 |
| `corporate.earnings` | `corporate_data` | Event V1, Observation V2 |
| `corporate.filing` | `regulatory_filing` | Evidence V2 |
| `fundamentals.observation` | `fundamentals` | Observation V2 |
| `news.article` | `news_evidence` | Evidence V2 |
| `events.feed` | `event_evidence` | Event V1, Evidence V2 |
| `macro.observation` | `macroeconomic_data` | Observation V2 |
| `macro.release_calendar` | `economic_calendar` | Event V1 |

The vocabulary is justified by active Jax market quote/OHLCV/trade/earnings/news/World Monitor/calendar mechanisms plus the committed Phase 03 core-source plan for instrument/company reference data, SEC filings/XBRL facts, FRED/ALFRED observations, and economic releases. It does not reproduce a vendor catalogue, alternative-data inventory, broker/trading methods, AI completion methods, analytics, recommendations, or speculative Fincept connectors.

Category and output mapping are normative for each capability ID. A declaration with the wrong category, missing output, extra/ambiguous output, reordered output, unsupported version, or different family fails closed. This makes provider substitution meaningful: research code can depend on a Jax capability and canonical family rather than vendor method/DTO names.

## Canonical-output relationship

Capabilities declare exact `canonical.ContractSchemaRef` destinations, not Go payload types. Only external information families are permitted:

- Instrument;
- Issuer;
- Event;
- Evidence;
- Observation.

Evidence and Observation destinations require the accepted provenance-bearing V2 contracts. Instrument, Issuer, and Event retain their accepted V1 schemas because Phase 01 did not introduce V2 for those families.

ResearchRun, QuantResult, and Recommendation are excluded. They are Jax-derived products and cannot be claimed as a raw provider capability output. The registry performs no conversion and does not assert that a raw response is already canonical.

## Raw/provider versus canonical boundary

Each capability carries `RawRepresentation`:

- `boundary` must be exactly `PROVIDER_RAW`;
- `format` is a closed representation class (`JSON_DOCUMENT`, `STRUCTURED_MESSAGE`, `TABULAR`, `BINARY`, or `STREAM_MESSAGE`);
- `schema` is a separate Phase 01 `VersionIdentity` for the provider payload/DTO schema;
- optional `media_type` is validated but contains no bytes.

A declaration attempting to label its boundary `CANONICAL` is rejected. Provider DTOs remain in their owning implementation packages. No DTO or payload struct was added to `libs/contracts/canonical`, and no raw payload bytes/reference/storage are introduced.

This contract supplies mapping intent only. WP-02.03 must implement explicit normalizers that consume the later WP-02.02 immutable raw reference, validate the target canonical contract, and attach accepted Phase 01 provenance.

## Static support versus runtime state

Static `SupportStatus` is part of capability definition:

- `SUPPORTED`;
- `UNAVAILABLE` for a known adapter contract that cannot supply the capability;
- `DISABLED` for a Jax policy-level prohibition independent from deployment configuration.

`DEGRADED` is deliberately not a static support value. Dynamic state is a separate versioned `CapabilityRuntimeState` with:

- provider identity and capability ID;
- `UNKNOWN`, `HEALTHY`, `DEGRADED`, `UNAVAILABLE`, or `DISABLED` runtime status;
- explicit `UNKNOWN`, `FRESH`, or `STALE` freshness;
- explicit `UNKNOWN`, `ACCEPTABLE`, `DEGRADED`, or `REJECTED` quality;
- bounded reason code where failure/degradation needs explanation;
- UTC observation time.

`ValidateRuntimeState` verifies the snapshot separately against a provider definition. It rejects mismatched providers, undeclared capabilities, healthy-but-stale/poor-quality states, unavailable-with-fresh-acceptable data, degraded rejected data, and runtime states that contradict a static `UNAVAILABLE` or `DISABLED` declaration.

The registry neither stores nor gathers runtime snapshots. This is only the attachment boundary required for WP-02.04/WP-02.05.

## Freshness and quality boundary

Static `OperationalSemantics` declares applicable delivery classes (`SNAPSHOT`, `HISTORICAL`, `STREAM`, `EVENT`) and freshness classes (`REAL_TIME`, `DELAYED`, `END_OF_DAY`, `EVENT_DRIVEN`, `PERIODIC`, `ON_DEMAND`). Every capability requires `CANONICAL_VALIDATION_REQUIRED` quality semantics.

These are labels, not policy engines. WP-02.01 does not define durations, choose a current feed tier, calculate age, select last-known-good data, retain state, poll providers, retry, back off, or score sources.

## Authentication and configuration boundary

The closed authentication classes are supported by repository evidence:

| Class | Existing evidence |
| --- | --- |
| `NONE` | World Monitor/local calendar and unauthenticated service boundaries |
| `API_KEY` | Polygon, Financial Datasets, Finnhub, NewsAPI, hosted embedding/provider clients |
| `API_KEY_PAIR` | Alpaca key plus secret |
| `AUTHENTICATED_SESSION` | Interactive Brokers gateway/bridge session |

OAuth and other unobserved classes were not added speculatively. The contract contains no credential value, token, password, secret location, header, endpoint, base URL, local path, account, feed/tier selection, timeout, priority, cache, or enabled flag. Strict JSON decoding rejects unknown fields, including attempted `credential_value` material.

Existing environment/config types such as `marketdata.ProviderConfig`, `utcp.ProviderConfig`, World Monitor environment variables, and embedding configuration remain runtime-owned. They may later select/configure an adapter associated with a stable provider definition, but they do not define provider identity.

## Version strategy

The implementation keeps distinct version roles:

| Role | Contract |
| --- | --- |
| Registry schema | `jax.provider_registry/v1` |
| Provider-definition schema | `jax.provider_definition/v1` |
| Capability schema | `jax.provider_capability/v1` |
| Runtime-state attachment schema | `jax.provider_capability_state/v1` |
| Provider API/vendor version | optional `VersionIdentity` in `ProviderAPIVersion` |
| Adapter implementation version | required `VersionIdentity` in `AdapterVersion` |
| Provider raw schema/DTO version | required `VersionIdentity` in `RawRepresentation.Schema` |
| Canonical output schema | exact `ContractSchemaRef` per output family |

Empty, unknown, and future versions fail closed. A schema change requires a new explicit contract version; provider API, adapter build, provider raw schema, and canonical Jax contract versions cannot be collapsed into one generic string.

No persisted or derived data is added. When future adapters emit derived Evidence/Observation, the normative V2 destinations require the Phase 01 provenance identities.

## Validation and negative paths

Deterministic tests and validators reject:

- unsupported registry, provider-definition, capability, and runtime-state versions;
- empty/malformed accepted `ProviderIdentity` and invalid versions;
- duplicate provider registration and ambiguous namespace ownership;
- duplicate capabilities;
- unknown/vendor-shaped capability IDs and wrong categories;
- unknown support, auth, raw format, delivery, freshness, quality, and runtime states;
- missing provider raw schema or a provider DTO described as canonical;
- no canonical output, extra/ambiguous output, wrong family, wrong ordering, or wrong output version;
- any external capability mapped to ResearchRun, QuantResult, or Recommendation;
- missing/invalid adapter or provider API versions;
- secret-bearing unknown JSON fields, invalid UTF-8, trailing JSON values, and invalid serialized versions;
- provider/runtime identity mismatch and undeclared runtime capability;
- healthy/stale/degraded contradictions and static/runtime support contradictions.

Validation returns typed `ValidationError` or `RegistryError`. Registration validates before mutation, and deterministic tests prove failed registration retains no entry.

## Fincept and external-library assessment

The committed Fincept evidence was used at concept level:

- DataHub makes producer ownership, freshness, errors, and last-known-good first-class target concepts;
- DataNormalizationService separates raw and normalized representations;
- the connector manifest is a discovery catalogue containing dormant/unwired entries and is not capability proof.

WP-02.01 adopts only static ownership, raw/canonical separation, and the future operational-state attachment point. TTL/last-known-good, normalization, health, rate control, and connector breadth remain deferred. No Fincept source, schema, class/file hierarchy, or dependency was copied.

No external registry/service-discovery/schema framework is justified. The requirement is a process-local deterministic Go catalogue and closed typed vocabulary; Go maps/slices, `sort`, `encoding/json`, and the accepted canonical contracts provide the needed mechanics with lower operational and compatibility cost.

## Rejected alternatives

1. Put provider DTOs or capability records in `libs/contracts/canonical`: rejected because canonical owns universal normalized domain/provenance semantics, not provider catalogues or raw schemas.
2. Put the registry in `libs/marketdata`: rejected because news, events, macro, filings, reference data, and calendars would depend on an active vendor/market client.
3. Create a new service, database table, distributed registry, or discovery platform: rejected because no current consumer needs coordination or persistence.
4. Use provider names, URLs, endpoints, or configuration IDs as provider identity: rejected in favor of the accepted typed `pvd_` identity.
5. Use free-form capability strings/maps: rejected because known Jax needs have closed category/output semantics and fail-closed validation.
6. Model capabilities as existing `GetQuote/GetCandles/GetNews` methods: rejected because provider method shape would leak into research replacement logic.
7. Treat static support and runtime health as one status: rejected because provider support is stable metadata while degradation/freshness/quality are observed state.
8. Add OAuth or vendor-advertised capabilities speculatively: rejected because current Jax evidence does not require them.
9. Implement adapters, normalization, raw retention, TTL, retries, health probes, or scoring as proof: rejected as later work-package scope.
