## Operation identity and repeatability

`Operation` is versioned as `jax.provider_operation/v1` and binds the complete accepted `ProviderIdentity`, `CapabilityID`, operation kind, and explicit retry safety.

The bounded data-provider operation kinds are:

- `READ_FETCH`;
- `PAGINATED_READ`;
- `STREAM_ESTABLISH`;
- `METADATA_FETCH`.

No broker, order, execution, recommendation, or speculative trading operation exists. `SAFE_REPEATABLE` permits policy-authorized retry; `SINGLE_ATTEMPT` fails a transient error without retry. A read-shaped call is not inferred safe from a method or protocol verb.

Instrumentation excludes an endpoint, URL, symbol, page token, request ID, payload ID, or arbitrary request identity.

## Failure and retry classification

The operational taxonomy separates:

- retry candidates: `TRANSPORT_TRANSIENT`, `PROVIDER_SERVER_ERROR`, `TEMPORARY_UNAVAILABLE`, `RATE_LIMITED`, and explicitly policy-controlled `ATTEMPT_DEADLINE`;
- non-retryable provider/caller/data failures: authentication, authorization, malformed request, not found, conflict, unsupported capability, provider-payload parse, canonical validation, provenance mismatch, and explicit permanent rejection;
- caller-control terminal states: `CALLER_CANCELLED` and `OVERALL_DEADLINE`.

`RetryPolicy.RetryableFailures` must explicitly list retryable classes. Invalid policy cannot mark authentication, parse, canonical validation, provenance, or another permanent class retryable. `ClassifyTransportError` recognizes context cancellation/deadline, bounded network/EOF/reset/refused evidence, and treats an unknown error as permanent rather than retrying because an error exists.

`ProviderFailure` carries either an HTTP status for policy classification or one explicit non-HTTP failure class. It cannot simultaneously smuggle a conflicting HTTP class. Its unwrap-able cause is not rendered in operational error text or instrumentation.

## HTTP status classification

`jax.provider_failure_classification_policy/v1` owns the exact mapping and optional versioned status overrides.

| Status | V1 base class | Retry eligibility |
| --- | --- | --- |
| 400 | `MALFORMED_REQUEST` | no |
| 401 | `AUTHENTICATION` | no |
| 403 | `AUTHORIZATION` | no |
| 404 | `NOT_FOUND` | no |
| 408 | `TRANSPORT_TRANSIENT` | only for repeatable operation and explicit retry policy |
| 409 | `CONFLICT` | no by default |
| 425 | `TEMPORARY_UNAVAILABLE` | policy-controlled |
| 429 | `RATE_LIMITED` | policy-controlled |
| 500, 502 | `PROVIDER_SERVER_ERROR` | policy-controlled |
| 503, 504 | `TEMPORARY_UNAVAILABLE` | policy-controlled |
| 501 | `UNSUPPORTED_CAPABILITY` | no |
| other 4xx/5xx | `PERMANENT_PROVIDER_REJECTION` | no |

The layer therefore does not blindly retry all 4xx or 5xx. An exception such as retryable 409 is a concrete `HTTPStatusOverride` under a different/exact policy identity/version, never a provider-name guess.

## Retry budget and terminal semantics

`RetryPolicy` is versioned as `jax.provider_retry_policy/v1` and explicitly records:

- maximum attempts, bounded to 1..20;
- maximum elapsed window, bounded to 24 hours;
- positive per-attempt timeout not exceeding the elapsed window;
- exact retryable failure classes;
- exact backoff strategy.

There is no recursion or infinite retry. Before every attempt the executor checks caller context, elapsed budget, static capability support, and local rate state. `retry_budget_exhausted`, `elapsed_budget_exhausted`, cancellation, deadline, and non-retryable failure are distinct terminal errors. Failed results have no raw bytes and cannot become a `RawPayloadRef` or canonical record.

All executable values in tests are synthetic. This package declares no production provider attempt count or timeout.

## Backoff and jitter

`BackoffPolicy` defines positive initial delay, finite multiplier, maximum delay, and an explicit `NONE` or `PROPORTIONAL` jitter strategy. Exponential calculation saturates at the maximum delay and rejects overflow/non-finite configuration.

Proportional jitter requires an injected `JitterSource`, consumes a value in `[0,1]`, and bounds output at the policy maximum. The representative proof uses `NONE`; jitter tests use fixed values and never seed from a clock or ambient random source.

The deterministic core never calls `time.Sleep`. `SystemTimeSource` is the production adapter and uses a context-aware timer; tests inject a clock/sleeper/timeout implementation that advances exact synthetic time.

## Retry-After

`ParseRetryAfter` supports:

- unsigned delta seconds;
- an HTTP-date parsed with Go's standard HTTP-date semantics.

Past absolute dates yield zero delay. Empty, signed/negative, non-date text, oversized, or CR/LF-bearing values fail as malformed. A parsed provider delay greater than `RateLimitPolicy.MaximumProviderDelay` fails as `retry_after_exceeds_maximum`; it is never silently capped. A delay that cannot fit the remaining retry elapsed budget or caller deadline fails as `retry_after_cannot_be_honoured`.

The scheduled delay is the maximum of deterministic backoff, valid provider Retry-After, and any known local/provider reset delay. A 429 is recorded separately. Successful completion of the injected sleep sets `RetryAfterDecision.Honoured=true`; cancellation during the wait leaves it unhonoured and terminates promptly.

## Static rate policy and runtime state

`RateLimitPolicy` is versioned as `jax.provider_rate_limit_policy/v1` and declares:

- request count per fixed window;
- window duration;
- capability concurrency limit;
- maximum permitted provider delay.

Values are adapter/configuration inputs, not hard-coded vendor quotas. Tests use synthetic values only.

`RateLimiter` is a concurrency-safe process-local state machine keyed by stable provider ID plus capability. It tracks local window use, in-flight concurrency, provider-reported remaining/reset state, and temporary provider exhaustion. `MayAttempt` is non-mutating and answers allowed/reason/retry time; `Acquire` consumes one request and concurrency slot; `Release` frees concurrency. Provider remaining/reset observation is distinct from the static policy.

The accepted immutable provider registry is not a mutable counter store. No rate state is persisted.

## Cancellation and deadlines

The executor checks caller cancellation/deadline before attempts and uses an injected per-attempt timeout context. Cancellation interrupts backoff through `Sleep(ctx, delay)` and no future attempt is made.

Caller cancellation and overall deadline are health-neutral. Per-attempt deadline is a separate class: retry eligibility is explicit in retry policy, and health impact is independently controlled by `HealthPolicy.CountAttemptDeadline` (false in the representative proof). This prevents a local deadline from automatically becoming provider-outage evidence.

## Health model and transitions

`HealthAssessment` reuses the accepted WP-02.01 statuses:

- `UNKNOWN`;
- `HEALTHY`;
- `DEGRADED`;
- `UNAVAILABLE`;
- `DISABLED`.

It is provider/capability scoped and records bounded reason, assessment time, last success/failure, consecutive counts, exact health policy identity, and operational component/build identity. It contains no freshness or canonical-data quality field.

`HealthPolicy` is versioned as `jax.provider_health_policy/v1` and makes explicit:

- consecutive failure threshold for degradation;
- consecutive failure threshold for unavailability;
- consecutive success recovery threshold;
- assessment horizon;
- whether per-attempt deadline is provider evidence.

The thresholds are synthetic proof values, not production claims. Operational transitions are deterministic and reject out-of-order evidence.

Health-affecting inputs:

- transport/server/temporary failures affect consecutive thresholds;
- rate-limit exhaustion degrades with `rate_limit_exhausted`;
- authentication/authorization makes the Jax capability operationally unavailable with a configuration-specific reason; this does not claim the provider's whole service is down;
- a registered-but-disabled/unavailable capability remains consistent with its static support declaration;
- successes recover only after the explicit success threshold.

Health-neutral inputs:

- caller cancellation and overall deadline;
- malformed request, not found, conflict, and request-specific permanent rejection;
- provider-payload parse, canonical validation, and provenance mismatch;
- per-attempt deadline unless the exact health policy opts in.

`Snapshot` returns `UNKNOWN/assessment_horizon_elapsed` after evidence ages beyond the horizon. A later observation resets expired consecutive counters before applying new evidence, so an old failure cannot contribute to a new threshold. It does not derive long-term trust or reliability.

## Health is not freshness

WP-02.04 remains authoritative for exact datum freshness and LKG. `HealthAssessment` has no `FreshnessState`, TTL, age, LKG mode, candidate, or fallback operation.

The following remain valid:

```text
provider capability HEALTHY      + a particular datum STALE
provider capability UNAVAILABLE  + a previously acquired datum FRESH
provider capability DEGRADED due to rate limit + WP-02.04-qualified LKG usable
```

`AsRuntimeState` is only an integration projection into the accepted WP-02.01 aggregate attachment. The caller must supply independent freshness and quality, after which existing `ValidateRuntimeState` rules apply. A projection failure does not mutate the `HealthAssessment` or a WP-02.04 freshness evaluation.

No stale fallback occurs inside `OperationalExecutor`. A provider failure remains a provider failure; a later caller may separately invoke WP-02.04 resolution.

## Successful raw-payload handoff and failure isolation

`ProviderAttemptResult` is either:

- exact non-empty raw bytes and no failure; or
- a typed failure and no raw bytes.

Mixed/partial success fails closed. `ExecutionResult.RawBytes` is populated only for `SUCCEEDED`. The representative test passes those exact bytes to accepted `PersistRawPayload`, retrieves them, and verifies their accepted SHA-256 content identity. The operational layer performs no JSON decoding, normalization, canonical validation, persistence, or fallback.

A terminal failure returns `FAILED`, typed terminal/failure identity, attempt/retry evidence, policy identities, and no raw bytes. It cannot publish fake raw or canonical success.

## Instrumentation and metrics cardinality

The package owns typed `OperationalEvent` observations for:

- attempts;
- scheduled/completed retries and backoff decisions;
- local throttling;
- provider rate-limit responses;
- success;
- terminal failure;
- health transitions.

`MemoryInstrumentation` is a deterministic proof sink. Future runtime adoption may adapt these events to existing Jax logs/Prometheus counters without changing execution semantics. No monitoring platform is introduced.

Bounded dimensions are provider identity, capability, operation kind, event kind, typed failure/disposition, retry delay/source, typed health state/reason, and exact component/policy identities. Events cannot carry URL, symbol, raw payload ID/body, request ID, arbitrary error string, headers, cookies, credentials, or API keys. The test injects a secret-bearing cause and proves neither error text nor serialized events expose it.

## Circuit-breaker decision and dependency assessment

A new circuit breaker is not required for WP-02.05. Explicit repeatability, per-operation maximum attempts, maximum elapsed time, per-attempt timeout, bounded backoff, rate admission, and capability health provide the required bounded behavior and diagnostics. Automatically refusing all calls because health is unavailable would also prevent ordinary recovery unless a separate probe/half-open state were added.

The existing `gobreaker` wrapper was inspected. Reuse would import a new module into `libs/contracts`, retain ambient-time behavior in proof tests, classify arbitrary errors as breaker failures, and provide provider-global rather than capability-scoped state. A second half-open state machine would add complexity without an authorized adopter. It remains a later adapter decision.

Go standard-library context, time, HTTP-date, network-error, synchronization, and math primitives plus accepted Jax contracts are sufficient. No external dependency was added. Fincept remains concept-only through committed Phase 02 reference notes; no source/schema/topology was copied.
