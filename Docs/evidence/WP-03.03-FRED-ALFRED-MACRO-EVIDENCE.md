# JAX HANDOVER — WP-03.03 FRED/ALFRED MACRO EVIDENCE

Status: IMPLEMENTED

## Provider and scope

The adapter is `libs/fred` and uses one logical provider identity:

- provider: `pvd_fred`, namespace `fred.alfred.data_api`, external slug
  `fred-alfred`;
- capability: `macro.observation`;
- logical source: `src_fred_economic_data`;
- qualification: **NOT_ASSESSED**. FRED is an official Federal Reserve Bank
  of St. Louis distribution platform, but a FRED-hosted series may originate
  from another institution. This package does not make a universal authority
  or trust-score claim.

The selected official FRED API v1 endpoints are:

- `fred/series` for series metadata;
- `fred/series/observations` for bounded native observations;
- `fred/series/vintagedates` for bounded vintage-date history.

The implementation follows the official [series documentation](https://fred.stlouisfed.org/docs/api/fred/series.html),
[observations documentation](https://fred.stlouisfed.org/docs/api/fred/series_observations.html),
[vintage-date documentation](https://fred.stlouisfed.org/docs/api/fred/series_vintagedates.html),
and [real-time-period guidance](https://fred.stlouisfed.org/docs/api/fred/realtime_period.html).
FRED and ALFRED are represented as views of the same provider identity; mode,
vintage date, realtime period, and source metadata carry the distinction.

## Credential and raw evidence policy

`FRED_API_KEY` is required by `LoadConfigFromEnv`; the key must be a
32-character lowercase alphanumeric value. `FRED_BASE_URL` is optional and
defaults to the official API base. The key is used only to construct the
outbound request query. It is not present in `RawPayloadRef`, raw-payload
metadata, provenance, typed errors, or logs. Tests use a deterministic fixture
key and never require a real credential. The official [API-key documentation](https://fred.stlouisfed.org/docs/api/api_key.html)
defines the key shape and requirement.

Successful response entity-body bytes are captured before decoding and passed
to the shared `provider.PersistRawPayload`. The shared raw store verifies size,
SHA-256, and exact retrieval before the deterministic parser is called. Each
series, vintage page, and observations page gets its own raw payload reference;
documents are never merged into synthetic raw evidence. The implementation
accepts the existing `provider.RawPayloadStore` port and is compatible with
the durable PostgreSQL store used by runtime composition. No FRED-specific
table or migration was added.

The provider uses the shared Phase 02 `OperationalExecutor` for retries,
rate-limiting, typed HTTP failure classification, health, and cancellation.
No FRED-specific retry stack was introduced. Request URLs are not stored as
evidence metadata.

## Series metadata and observations

`macroevidence.MacroSeries` and `macroevidence.MacroObservation` are
provider-neutral research-facing wrappers. The private JSON structs used at the
HTTP boundary do not escape the adapter package. `MacroSeries` preserves provider series ID, title, observation bounds,
frequency and code, units and short units, seasonal adjustment and code,
last-updated metadata, notes, requested information state, provider realtime
metadata, source payload, and provenance. Empty optional source fields remain
empty; frequency, units, and
seasonal adjustment are never inferred from title or notes.

`MacroObservation` preserves the series reference and provider series ID,
date-only observation date, source value text, derived finite `float64` value
when present, explicit source-missing state, returned realtime start/end,
requested information-state mode, acquisition time, source payload, and
provenance. FRED's `.` marker remains `Present=false`, `SourceValue="."`,
and no numeric zero is substituted. The source lexical value remains
authoritative when a convenience numeric value is also supplied.

The baseline request path always sends `units=lin`, `output_type=1`, ascending
observation order, and no frequency or aggregation parameters. Server-side
transformations and frequency aggregation are therefore not enabled. An
explicit `INITIAL_RELEASE` mode is represented with `output_type=4`; it is not
blurred into current or revised data.

## Vintage and information-state semantics

`InformationState` requires an explicit mode and is carried on both
`MacroSeries.RequestedInformation` and `MacroObservation.RequestedInformation`:

- `CURRENT` requests the current FRED view;
- `AS_OF_REALTIME_DATE` sends equal `realtime_start` and `realtime_end` dates;
- `VINTAGE_DATE` sends an explicit `vintage_dates` date;
- `INITIAL_RELEASE` requests the documented initial-release output type.

Series metadata is requested with the same current/as-of state as observations.
For `VINTAGE_DATE`, because `fred/series` has no `vintage_dates` parameter, the
adapter uses the compatible equal-date `realtime_start`/`realtime_end` view.
FRED has no series-level initial-release mode, so initial-release observations
explicitly use current series metadata and retain that distinction on
`MacroSeries`; they do not claim that metadata is an initial-release snapshot.

There is no implicit `GetMacro(series, year)`-style current fallback. A caller
requesting historical-as-known data must choose an historical mode and date.
The requested mode is retained on every normalized observation, while the
returned `realtime_start` and `realtime_end` remain separate source fields.

Vintage and realtime values use the package `Date` type. No date-only value is
converted to midnight UTC and no release timestamp is fabricated. Acquisition
time is the UTC `RawPayloadRef.ReceivedAt` and is never used as a vintage or
realtime boundary.

Observation identity includes series, observation date, returned realtime
period, source lexical value, and requested information-state semantics. Thus
the same observation date with different historical states or revised values
does not overwrite an earlier normalized value. Selection of latest, first
release, a particular vintage, or an as-of date remains an explicit caller or
research policy.

## Pagination and completeness

Vintage and observation requests use documented bounded `count`, `offset`, and
`limit` metadata and ascending ordering. The adapter follows additional pages
only up to the configured bounded `MaxPages`; each page is independently
persisted. Results are `COMPLETE` only after the acquired count equals the
reported count and every page boundary is globally increasing without
duplicates. A bounded page limit, invalid metadata, mismatched offsets,
changed counts, or malformed cross-page ordering fails closed as `INCOMPLETE`;
a partial or corrupt page cannot masquerade as complete.

## Canonical boundary and known contract gap

The existing canonical Observation V2 contract permits only instrument,
issuer, or event subjects and UTC timestamps. A macro series is not one of
those subjects, and FRED's observation/vintage/realtime boundaries are dates,
not asserted instants. WP-03.03 therefore uses a bounded provider-neutral
wrapper rather than a misleading canonical Observation projection or a broad
Phase 01 redesign. The wrapper carries the accepted canonical provenance
contract, ordered raw evidence references, input fingerprint, normalizer
identity/version, and all macro temporal semantics needed by research.

The provider-neutral package is `libs/macroevidence`; `libs/fred` exposes only
compatibility aliases for adapter callers. The wrapper contains no FRED
response DTO or endpoint-array layout. The provider capability advertises the
versioned `jax.macroevidence` provider-neutral output contract and does not
claim Canonical Observation V2. A future official BEA/BLS adapter can project
into the same `MacroSeries` and `MacroObservation` representation. If macro
observations later require first-class canonical persistence/querying, a
separately reviewed versioned canonical contract is required.

Freshness is not invented for immutable historical evidence. Observation age,
vintage/realtime information state, and acquisition time remain distinct;
downloading a 2020 vintage in 2026 does not make the economic information
state current. Existing Phase 02 freshness policies remain caller-owned.

## Verification

Deterministic tests in `libs/fred/fred_test.go` cover provider identity and
provider-neutral capability declaration, explicit credential validation and secret exclusion,
exact raw bytes and SHA-256, raw persistence failure, metadata preservation,
date-only semantics, native numeric precision representation, missing values,
realtime periods, state-aligned series metadata, current versus as-of queries,
initial-release `output_type=4`, cross-page ordering/duplicate rejection,
pagination/completeness, trailing and duplicate JSON, series mismatch, and
provider-neutral output.
The current/as-of regression returns an earlier fixture value for an explicit
historical request and a later revised fixture value only for the explicit
current request, proving that the current response cannot satisfy the
historical contract accidentally.

Live FRED verification was **NOT PERFORMED** because no approved API key was
configured. Deterministic tests do not require one.

No database migration, release calendar, economic release event, release time,
alert, trading-event mapping, execution, order, broker, recommendation, or
hosted model inference work was started. Economic release/calendar ingestion
belongs to WP-03.04.
