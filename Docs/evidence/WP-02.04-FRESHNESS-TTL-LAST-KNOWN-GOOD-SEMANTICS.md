## Ownership and dependency direction

Freshness policy, temporal evaluation, LKG policy/selection, and their typed failure model extend `libs/contracts/provider`. That package already owns stable capability identity, immutable raw acquisition references, normalization routes, and the acceptance envelope. Canonical remains the sole owner of domain meaning and provenance primitives.

```text
provider raw bytes/reference
          |
WP-02.03 accepted NormalizationResult
          |
canonical validation + immutable output/provenance identity
          |
provider FreshnessPolicyRegistry + caller-supplied evaluation time/status
          |
FreshnessEvaluation (one exact datum)
          |
explicit LastKnownGoodPolicy, only when current data is unusable
          |
FreshnessResolution (selected exact datum + visible fallback state)
```

The dependency remains one way: `provider -> canonical`. Canonical does not import provider contracts and gains no TTL, cache, vendor, provider-health, or fallback vocabulary.

Rejected owners:

1. `libs/contracts/canonical`: freshness is provider/data-platform policy, not universal domain meaning.
2. `libs/marketdata`: the policy also covers filings, macro, news, events, calendars, and reference data.
3. runtime cache/provider clients: their eviction/failover concerns cannot establish canonical observation freshness.
4. a new service/database/configuration platform: the required proof is deterministic and process-local.

## Freshness policy design

`FreshnessPolicy` is versioned as `jax.provider_freshness_policy/v1` and contains:

- an accepted `canonical.ComponentIdentity` of kind `policy`, including exact stable identity and namespaced version;
- stable Jax `CapabilityID`, exact canonical target schema, and bounded `RESEARCH`, `DISPLAY`, or `DECISION_SUPPORT` use class;
- validity mode, authoritative timestamp role, fresh horizon, expiry horizon, bounded future skew, and missing-timestamp behavior;
- a separately versioned `LastKnownGoodPolicy` (`jax.provider_lkg_policy/v1`).

Policies are provider-neutral. Provider names, endpoints, tiers, health, source scores, licensing, costs, and preference are absent. A provider-specific exception would require a new explicit versioned policy declaration rather than a hidden conditional, but no such exception was justified here.

`FreshnessPolicyRegistry` is a deterministic in-memory registry. Lookup requires exact capability, canonical target, use class, and policy `ComponentIdentity`/version. It rejects duplicate IDs, changed meaning under an existing ID, ambiguous declarations for the same semantic/version route, unknown identity, version mismatch, and capability/target mismatch. It performs no dynamic loading or persistence.

No production TTL values are declared. All executable durations are synthetic test policy values. This avoids inventing provider/data-class service levels before an adopting package has evidence.

## Validity modes and freshness states

The policy modes are:

| Mode | Meaning |
| --- | --- |
| `AGE_BOUNDED` | An authoritative canonical timestamp starts a fresh horizon and a distinct expiry horizon. |
| `UNTIL_SUPERSEDED` | The active datum remains fresh until explicit immutable lifecycle evidence makes it superseded/retracted/disputed/invalidated. No huge duration represents infinity. |
| `NOT_APPLICABLE` | Age freshness is explicitly not the governing temporal dimension. No timestamp/TTL is silently invented. |

`TemporalQualityState` is deliberately separate from WP-02.01 `CapabilityRuntimeState` and from WP-02.03 `NormalizationQuality`:

| State | Exact meaning |
| --- | --- |
| `FRESH` | Age is strictly less than `FreshFor`, or an active `UNTIL_SUPERSEDED` policy applies. |
| `STALE` | Age is greater than or equal to `FreshFor` and strictly less than `ExpireAfter`. It is not directly upgraded or accepted as fresh. |
| `EXPIRED` | Age is greater than or equal to `ExpireAfter`; it is ineligible for LKG. |
| `UNKNOWN` | A required authoritative timestamp is absent and the versioned policy explicitly chooses `UNKNOWN` rather than failure. |
| `NOT_APPLICABLE` | The policy explicitly says age freshness is not applicable. |

Invalid canonical data is not a freshness state. It produces `invalid_canonical_input`. Invalid provenance is separately `invalid_provenance_input`.

## Timestamp authority

The policy chooses exactly one role from:

- `OBSERVED_AT`;
- `PUBLISHED_AT`;
- `COLLECTED_AT` only when explicitly authoritative;
- `OCCURRED_AT`;
- `EFFECTIVE_AT`;
- `EFFECTIVE_FROM` for reference records;
- `DATASET_AS_OF` from an immutable dataset snapshot/vintage;
- `NONE` only for modes that do not calculate age.

`created_at` is intentionally unsupported as a freshness clock. `RawPayloadRef.ReceivedAt` remains acquisition/provenance evidence and is never substituted for a canonical observation/publication/effective/as-of time. A fresh HTTP receipt containing an old observation therefore evaluates from the old `Observation.ObservedAt`.

`DATASET_AS_OF` accepts exactly one distinct immutable dataset as-of timestamp from canonical dataset snapshot/provenance inputs. No timestamp yields policy-directed failure/unknown; multiple distinct vintages yield `ambiguous_authoritative_timestamp`.

Market session/calendar validity is not guessed from wall time. A later capability adapter may choose an explicit effective/publication/as-of policy or use `NOT_APPLICABLE` where session-window semantics remain feature-owned. No exchange calendar service is introduced.

## Explicit evaluation time and knowledge cutoff

`FreshnessEvaluator.Evaluate` and `FreshnessEvaluator.Resolve` require a non-zero UTC evaluation time and an explicit `CURRENT_STATE` or `HISTORICAL_REPLAY` context. There is no `time.Now()` call in the freshness implementation.

The evaluator also rejects an immutable record whose raw acquisition completed after the supplied evaluation time (`record_not_yet_available`). This prevents historical replay from using data that Jax did not yet possess.

Given the same accepted normalization result, lifecycle inputs, policy versions, candidate set, context, and evaluation time, the result is identical.

## TTL and expiry boundaries

For an age-bounded policy:

```text
age < FreshFor                         => FRESH
FreshFor <= age < ExpireAfter          => STALE
age >= ExpireAfter                     => EXPIRED
```

Therefore `age == TTL` is **STALE**, and `age == expiry horizon` is **EXPIRED**. Zero or negative fresh TTL is invalid. `ExpireAfter` must be strictly greater than `FreshFor`, avoiding overlapping states and ensuring a meaningful stale interval. Negative future-skew allowance is invalid.

No fuzzy comparison or implicit grace period exists.

## Future timestamps and clock skew

An authoritative timestamp after evaluation time yields a negative age; age is never clamped to zero. It is accepted as `FRESH` only when the negative age falls inside the policy's explicit, versioned `AllowedFutureSkew`, and `WithinFutureSkew` remains visible. Beyond the tolerance, evaluation fails as `future_timestamp_beyond_allowed_skew`.

The proof uses a canonical scheduled Event with an effective time three seconds ahead and a five-second test tolerance, then rejects the same shape six seconds ahead. Its raw acquisition predates evaluation time, so future semantic time and future knowledge are not conflated.

## No-expiry, supersession, and retraction semantics

`UNTIL_SUPERSEDED` returns `FRESH` without an arbitrary long duration while lifecycle is active. `TemporalRecordLifecycle` is immutable status input with:

- `ACTIVE`;
- `SUPERSEDED`;
- `RETRACTED`;
- `DISPUTED`;
- `INVALIDATED`.

Every non-active status requires a UTC `ChangedAt`.

`CURRENT_STATE` rejects any supplied non-active status. `HISTORICAL_REPLAY` may use that immutable record only when `ChangedAt` is strictly after the historical evaluation time; at or after the status change it is rejected. This distinguishes current truth from what was knowable before a later correction/retraction without implementing a history database.

Expired or inactive records are never selected as LKG.

## Last-known-good qualification

A `TemporalRecord` is not LKG merely because it was retrieved or inserted most recently. The evaluator verifies:

1. WP-02.03 status is `ACCEPTED` and quality is `CANONICAL_VALIDATED`;
2. every raw/parse/map/canonical/provenance validation stage succeeded;
3. raw reference, registered provider capability, normalizer identity, canonical validation, immutable canonical content, and exact raw provenance still verify;
4. capability, canonical target, subject, and semantic qualifier match the requested `FreshnessKey`;
5. lifecycle permits selection in the evaluation context;
6. the temporal state is `FRESH`, or is `STALE` under `FRESH_OR_STALE` policy;
7. a stale candidate carries an earlier matching `FRESH` evaluation which the evaluator re-runs and reproduces exactly;
8. age is within the explicit maximum fallback age.

Malformed, normalization-rejected, provenance-mismatched, unknown, expired, superseded, retracted, disputed, invalidated, cross-subject, cross-capability, and cross-policy candidates do not qualify.

## Deterministic LKG selection

Selection is independent of retrieval order, database row order, map iteration, and insertion time:

1. evaluate/filter all same-key candidates under the exact supplied policy/time/context;
2. order eligible candidates by authoritative timestamp descending;
3. use immutable record identity only to make processing/order deterministic;
4. if two different newest immutable records share the same authoritative timestamp, return `ambiguous_lkg_selection` rather than choosing an arbitrary correction/version.

Duplicate copies of the same immutable record collapse only when their temporal qualification is identical.

## Explicit stale fallback

`LastKnownGoodPolicy` modes are:

| Mode | Behavior |
| --- | --- |
| `PROHIBITED` | Any unusable/missing current record fails as `fallback_prohibited`. |
| `FRESH_ONLY` | A recent immutable record may be selected only if it is still `FRESH`. |
| `FRESH_OR_STALE` | A stale record may be selected only with reproducible prior-fresh qualification. |

Every allowed mode requires a positive maximum fallback age. `age == MaximumAge` is allowed; only `age > MaximumAge` fails. Expiry remains a harder bound even if maximum fallback age is longer.

`FreshnessResolution` exposes exact freshness and fallback facts rather than a `GOOD/BAD` aggregate:

- exact selected `ImmutableContractRef`;
- current record identity when supplied;
- exact freshness and LKG policy identities/versions;
- evaluation time/context, authoritative timestamp, age, and semantic key;
- WP-02.03 canonical quality;
- original `FRESH`/`STALE` state;
- `USED`/`NOT_USED` fallback status;
- fallback age, qualification mode, reproducible prior-fresh evaluation, and reason.

A selected stale datum remains `STALE`.

## Data freshness versus provider health

The evaluator does not inspect or produce provider operational health. It requires only a static accepted provider/capability declaration and an accepted datum.

These remain valid independent combinations:

- provider healthy, exact datum stale;
- provider unavailable, previously acquired datum still fresh.

WP-02.01 `RuntimeStatus` and the existing runtime-state attachment remain separate. WP-02.05 owns health production, polling, rate limits, retries, backoff, and operational instrumentation.

## Quality relationship

The result retains three independent facts:

```text
canonical normalization quality: CANONICAL_VALIDATED
temporal quality state:           STALE
fallback state:                   USED
```

Freshness cannot make invalid data canonical. LKG selection cannot upgrade stale data. Provider health cannot infer datum freshness. Source trust cannot alter calculated age.

## Provenance, version identity, and replay

Each evaluation records:

- exact canonical `ImmutableContractRef` and raw acquisition ID;
- exact normalizer `ComponentIdentity`;
- exact freshness policy `ComponentIdentity`/version;
- capability, target/use class, and semantic subject/key;
- evaluation time/context;
- authoritative timestamp role/value and calculated age;
- canonical quality, temporal state, lifecycle, and reason.

Each fallback resolution additionally records current/selected identities, exact LKG policy/version, fallback status/age/reason, and the reproducible prior-fresh evaluation when needed.

This is sufficient for later replay to ask: at historical time T under policy P, what state did record R have and which LKG candidate would deterministic selection choose? WP-02.04 does not build Phase 07 replay orchestration or a database/history engine.

## Failure taxonomy

`FreshnessError` has a closed `FreshnessErrorCode` and bounded safe detail. Material codes cover:

- unsupported/invalid policy version, invalid policy, TTL/skew error;
- invalid/non-UTC evaluation time and record not yet acquired at T;
- missing/ambiguous authoritative timestamp and future time beyond skew;
- semantic key, policy/capability/target, and policy-version mismatch;
- invalid canonical and invalid provenance input;
- superseded, retracted, disputed, and invalidated lifecycle;
- fallback prohibited, excessive fallback age, no acceptable LKG, and ambiguous LKG;
- missing/non-reproducible prior-fresh qualification;
- duplicate, ambiguous, or unknown registry policy.

Failures return no successful evaluation/resolution and never contain raw bytes, credentials, provider responses, or secrets.

## Representative deterministic proof

`TestFreshnessEvaluatorRepresentativeObservationV2Proof` and the LKG tests build on the accepted WP-02.03 synthetic macro Observation V2 normalizer and demonstrate:

1. exact raw bytes are persisted/retrieved and normalized to validated Observation V2;
2. explicit versioned freshness/LKG policy is registered;
3. fixed UTC evaluation time is supplied;
4. the record is `FRESH` immediately before TTL;
5. `age == TTL` is exactly `STALE`;
6. `age == ExpireAfter` is exactly `EXPIRED`;
7. a newer invalid current candidate is rejected;
8. an older canonical/provenance-valid same-key candidate with reproducible prior-fresh evaluation is selected;
9. resolution visibly says `fallback_status=USED` while selected state remains `STALE`;
10. `age == MaximumAge` is accepted and excessive age is rejected;
11. candidate permutations and repeated evaluation produce the same exact result;
12. no provider/network/database/logger/model/current-clock dependency participates.

Additional negative proof covers policy/version mismatch, missing timestamps, explicit `UNKNOWN`, recent raw receipt with old canonical observation, future skew, record-not-yet-known, invalid provenance, semantic mismatch, fallback prohibition, fresh-only policy, ambiguous equal-time records, missing prior-fresh proof, retraction, supersession, historical replay, and dataset-vintage authority/ambiguity.
