# WP-01.01 — Existing Jax Domain Contract Inventory

## Control and scope

- Work package: `WP-01.01 — Inventory existing Jax domain contracts before adding new ones`
- Controlling package: `Docs/Jax-Roadmap-v2/01-canonical-contracts-provenance-audit/WP-01.01-inventory-existing-jax-domain-contracts-before-adding-new-ones.md`
- Starting commit: `8f1007de7d88b5abee5f4cbfea5f026e8e995f5c` (`docs: version Jax Roadmap v2 baseline`)
- Branch: `capability-reset`
- Inventory date: 2026-08-21
- Scope: source contracts, runtime/API projections, persistence schemas, configuration contracts, and material frontend read models already present in Jax.
- Explicit exclusions: no new canonical contract, schema, migration, API, repository, service, runtime behavior, or Phase 00 causal-attribution change.

This is an evidence inventory, not a target model. Similar names are kept separate unless an actual conversion, shared persistence record, or producer/consumer relationship demonstrates equivalence.

## Method and classification

The inventory used type-declaration searches followed by source-reference tracing across `libs/`, `internal/`, `cmd/trader/`, `cmd/research/`, `frontend/src/data/`, and `db/postgres/migrations/`. A type is called runtime-active only when a non-test runtime path imports it, constructs it, scans it from storage, or exposes it through an API. Absence of a runtime import is evidence of isolation, not proof that a subsystem is obsolete.

Classification terms used below:

| Classification | Phase 01 interpretation |
| --- | --- |
| `KEEP` | Retain the existing contract and its ownership unless later evidence overturns it. |
| `KEEP BUT VERSION` | Evolve in place by adding explicit version/provenance identity later. |
| `CONSOLIDATE LATER` | Materially overlaps another Jax concept; choose a canonical meaning before migration. |
| `ADAPT AT BOUNDARY` | Keep as a provider, transport, persistence, or UI shape; map at its boundary. |
| `REPLACE LATER` | Deprecate only after a compatible replacement and migration decision. |
| `LEGACY` | Compatibility surface that must not silently become the Phase 01 canonical model. |
| `FEATURE-LOCAL` | Valid inside its bounded feature; do not promote to shared canonical status by default. |
| `TEST-ONLY` | Benchmark, replay, fixture, or harness contract rather than production domain state. |
| `NEEDS ARCHITECTURE DECISION` | Ownership or semantics cannot be selected safely by inventory alone. |

## Executive answers

1. **Important contracts today.** Jax has mature artifact, dataset, deterministic event-decision, asset-resolution, risk-policy, candidate/paper-review, AI benchmark, and memory contracts. It also has several older or feature-local Event, EvidenceBundle, Signal, Candidate, Recommendation, ResearchRun, and execution representations.
2. **Ownership.** Ownership is distributed among shared `libs/contracts`, `internal/domain/artifacts`, the active World Monitor path in `cmd/trader` plus `internal/modules/eventdecisions`, active candidate/approval modules, research runtime DTOs, and isolated `internal/decisioning`, `macroevents`, and `profitability` packages.
3. **Duplication.** The most material collisions are Event, EvidenceBundle/EvidenceItem, Signal/Candidate, Recommendation/Decision, Instrument/asset mapping, Risk, PaperTicket, Audit, Candle/Observation, and Backtest/ResearchRun.
4. **Strong identity/version/provenance.** Strategy artifacts, dataset snapshots, genuine event decisions, event asset resolutions, evidence subjects, and AI-shadow benchmark records are strongest. They use hashes, explicit versions, replay/idempotency identities, timestamp roles, or immutable history.
5. **Replay limits.** The active genuine-event decision path and Phase 00 AI benchmark are reproducible to a useful degree. Candidate lifecycle, generic audit events, orchestration/memory plans, macro-event upserts, live recommendation projections, and legacy execution records cannot reconstruct every input and policy version deterministically.
6. **Likely survivors.** Artifact trust, dataset hash lineage, deterministic asset resolution, versioned event decisions, evidence-subject identities, runtime safety policy, and shared service interfaces should be evolved rather than duplicated.
7. **Boundary-only shapes.** Provider payloads, HTTP request/response DTOs, SQL scan structs, AI raw/model results, frontend read models, and broker DTOs should remain adapters or projections.
8. **Decisions before design.** Phase 01 must decide canonical ownership, identity/time rules, provenance/version minimums, event/evidence semantics, research-run-to-result lineage, recommendation meaning, history mutability, and compatibility treatment of dormant/legacy subsystems.

## API, persistence, and frontend projection findings

Material API and frontend shapes are deliberately projections:

- Trader `Signal`, `OrchestrationRunRow`, `RecommendationRow`, and `Trade` in `cmd/trader/frontend_api.go:450,465,859,962` scan SQL rows directly. The frontend mirrors them in `frontend/src/data/types.ts:193,350,365`. They are coupled to column selection and JSON naming, not domain-owned contracts.
- World Monitor frontend types in `frontend/src/data/ai-service.ts:38,91,109,136` closely mirror inbox, subject, and decision query projections. The frontend decision omits several persisted fields, including the complete replay metadata and full timestamp/provenance set. This is appropriate for a read model but lossy for reconstruction.
- Candidate approval and paper-ticket frontend types in `frontend/src/data/approvals-service.ts:4,40,52,73,100` flatten active persistence rows and latest relationships. They should remain read models.
- General event types in `frontend/src/data/types.ts:620,635,654,658` represent normalized/raw/timeline projections and overlap but do not match World Monitor Event or macro Event field-for-field.
- Macro event/read models in `frontend/src/data/types.ts:756-892` align with the feature-local macro tables, not with World Monitor event decisions.
- Dataset/run types in `frontend/src/data/types.ts:510-618,720-753` expose useful lineage fields but make most fields optional and use untyped maps; they cannot enforce canonical invariants.

The current API boundary has no generated schema or shared version identity between Go and TypeScript. Compatibility is maintained by matching handwritten JSON fields and tests.
