## Ownership and dependency direction

The normalization registry, orchestration contract, staged failure model, loss metadata, and acceptance envelope extend `libs/contracts/provider`. This is the smallest owner because the package already owns provider/capability/raw-schema identity and the immutable raw reference/storage port.

```text
feature-owned provider DTO/parser/identity resolver
                         |
verified provider.RawPayloadRef + exact stored bytes
                         |
provider.Normalizer + exact normalizer descriptor/registry route
                         |
canonical Jax contract (canonical remains sole domain owner)
                         |
canonical validation + raw/provenance linkage validation
                         |
accepted provider.NormalizationResult
```

The dependency remains one way: `provider -> canonical`. Canonical has no provider/vendor import and no Polygon, Alpaca, Finnhub, World Monitor, FRED, SEC, endpoint, HTTP, or vendor-field vocabulary.

Rejected ownership alternatives:

1. `libs/contracts/canonical`: rejected because canonical owns universal Jax meaning and validation, not vendor parsing/mapping or raw routing.
2. `libs/marketdata`: rejected because normalization also covers filings, news, events, reference data, and macro observations.
3. A new service/module/framework: rejected because a deterministic shared Go boundary and process-local registry satisfy the current consumer and proof.
4. Existing `event_raw/event_normalized`: rejected because it is a feature-local mutable SQL projection and not an exact-byte, cross-provider canonical boundary.

## Normalizer contract

`NormalizerDescriptor` is versioned as `jax.provider_normalizer/v1` and binds:

- accepted `ProviderIdentity`;
- stable Jax `CapabilityID`;
- exact provider-raw boundary/format/schema/media expectation;
- exact mapping/normalizer `ComponentIdentity`, including its independent `VersionIdentity`, provider binding, and optional content identity;
- exact canonical `ContractSchemaRef` target.

`Normalizer.Normalize(context.Context, NormalizationInput)` consumes only an accepted raw reference and exact bytes. Implementations parse into provider-owned typed representations and map those values to a `NormalizationCandidate`. They do not fetch, retry, choose providers, call a model, inspect a log, or hide acquisition.

The candidate is not accepted data. It carries a canonical contract value, immutable output revision, and typed field dispositions. Any returned error discards the candidate. The pipeline returns a zero `NormalizationResult` on every rejection.

`EncodeNormalizerDescriptorJSON` and `DecodeNormalizerDescriptorJSON` provide stable strict descriptor serialization. Decode rejects unknown fields (including secret-bearing attempts), duplicates, nulls, invalid UTF-8, trailing values, invalid identities, and unsupported versions. The in-memory acceptance result deliberately has no persistence/JSON contract, avoiding a second canonical business model.

## Normalizer registry and routing

`NormalizerRegistry` is deterministic, process-local, and bound to the accepted provider registry. Its exact route is:

```text
complete registered ProviderIdentity
+ CapabilityID
+ provider raw boundary/format/schema version
+ target canonical family/version
```

Registration verifies the provider/capability declaration, static `SUPPORTED` state, exact raw expectation, authoritative WP-02.01 target mapping, provider-bound component identity, and descriptor version. A second normalizer for the same route is rejected as ambiguous, even when it claims a different mapping version. Deployment of a changed semantic mapping therefore requires an explicit registry replacement/configuration decision; it cannot be silently selected as “closest.”

At request time the caller supplies the exact expected normalizer component identity. A different component/version/content identity fails with `normalizer_version_mismatch`. Missing exact routes fail with `unknown_normalizer`. No endpoint strings, method names, heuristic matching, plugin discovery, dynamic loading, or fallback exists.

## Pipeline stages and acceptance

`NormalizationPipeline.Normalize` executes:

1. **RAW_VERIFICATION** - validate `RawPayloadRef`, byte count, and exact Phase 01 SHA-256 content identity.
2. **ROUTING** - verify registered provider, declared/supported capability, raw representation/schema, target schema, and exact normalizer identity.
3. **PARSING** - the selected adapter parses bytes into its provider-owned typed representation and returns parsing-specific typed errors.
4. **NORMALIZATION** - deterministic provider semantics, identities, clocks, units, and enums map to one canonical candidate.
5. **CANONICAL_VALIDATION** - call the canonical record's accepted `Validate()`; constructing a Go struct is not acceptance.
6. **PROVENANCE_VALIDATION** - bind provenance-bearing output to the exact raw content/provider/source/revision/receipt and selected component.
7. **ACCEPTANCE** - compute canonical content identity, validate an `ImmutableContractRef`, and return `ACCEPTED / CANONICAL_VALIDATED` with every stage marked complete.

`NormalizeStored` is a bounded bridge through the WP-02.02 `RawPayloadStore`: it retrieves and digest-verifies exact bytes, then calls the same pipeline. It performs no acquisition, network call, retry, or fallback.

Failures never return a partially accepted record, immutable output reference, or accepted status.

## Raw/provider versus canonical boundary

Provider DTOs are not added to production shared contracts. The representative test adapter has a typed `syntheticMacroRecord`, strict JSON parser, deterministic identity resolver, and explicit mapper. That DTO remains test/provider-owned and is not a canonical schema.

Canonical output is always one of the WP-02.01 authoritative external-information families:

- Instrument V1;
- Issuer V1;
- Event V1;
- Evidence V2;
- Observation V2.

ResearchRun, QuantResult, and Recommendation are rejected by descriptor/target validation because they are derived Jax products.

No provider-specific “almost canonical” output layer is introduced. `NormalizationCandidate` is only an unaccepted orchestration value containing an actual `canonical.Contract`.

## Provenance and forensic linkage

Every accepted result retains:

- the exact immutable `RawPayloadRef`, including its `rpa_` acquisition identity and raw `ContentIdentity`;
- exact selected mapping/normalizer `ComponentIdentity`;
- target canonical schema;
- exact canonical `ImmutableContractRef` and canonical content identity;
- validation-stage evidence and loss dispositions.

For Observation V2, the pipeline additionally requires canonical `Provenance` whose primary producer exactly equals the selected normalizer and whose `LineageInput` contains an `EvidenceRef` matching the raw content, provider, logical source, revision, and collection/receipt time. The observation source must match the raw logical source.

For Evidence V2, the required `ImmutableRef` must match the same raw content/provider/source/revision/receipt. If Evidence provenance is present, its producer must match the selected normalizer.

Instrument, Issuer, and Event have no accepted Phase 01 provenance-bearing schema. Their raw/component/output binding remains in the acceptance envelope rather than changing those frozen canonical versions.

Later replay can identify the acquisition, retrieve bytes through `RawPayloadStore`, verify byte count/digest, identify the component version/content, and verify the canonical output content. Raw bytes are referenced, not embedded in the canonical record.

## Source identity

Provider identity is always known. Source identity is never derived from provider name. The representative Observation normalizer requires a genuinely supplied raw `SourceIdentity` and revision plus a bounded resolver that maps the provider series to a canonical subject and matching `SourceReference`. Missing source/revision or resolver failure is an explicit `identity_resolution_failure`.

A future adapter may derive a source only when its mapping semantics provide deterministic evidence and must then document that rule. This package implements no generic provider-to-source inference.

## Loss and omission semantics

`FieldDisposition` is a bounded list, not a duplicate provider schema or `map[string]any` metadata. Each named provider field is exactly one of:

- `REPRESENTED`, with the canonical destination field;
- `INTENTIONALLY_OMITTED`, with a typed reason;
- `UNSUPPORTED_UNMAPPABLE`, with a typed reason and no stronger canonical claim.

Duplicate fields, unknown states, missing reason/destination metadata, contradictory entries, and a candidate with no represented information fail as `loss_metadata_inconsistent`. Invalid or ambiguous provider values are not accepted loss entries: they are typed mapping failures. Exact raw bytes remain the authoritative source for omitted provider-only detail.

The proof maps series, time, value, unit, and value kind; intentionally omits provider-only release state; and records display precision as unsupported/unmappable because the canonical numeric value already preserves the evidentiary number without inventing formatting semantics.

## Determinism and identities

There is no stochastic or AI boundary. Fixed raw bytes/reference, provider/capability/schema, target, mapping component, configuration identity (when a future adapter declares one), and deterministic resolver inputs must produce the same canonical bytes and immutable output reference.

`VerifyDeterministicNormalization` executes an identical request twice and rejects any canonical-byte, immutable-output, or loss-metadata change as `non_deterministic_output`. Tests prove both repeatability and rejection of a deliberately changing normalizer.

The representative adapter derives `obs_`, `evd_`, `pvn_`, and output-revision values from a documented versioned seed containing raw acquisition/content identity, exact normalizer identity/version, provider series, and normalized UTC observation time. It creates no UUID/random identity. The subject is resolved through a bounded deterministic catalogue interface. Future durable owner/catalog identity is not fabricated.

## Version strategy

The pipeline keeps these meanings distinct:

| Role | Identity |
| --- | --- |
| Raw reference contract | `jax.provider_raw_payload_ref/v1` |
| Provider raw/DTO schema | `RawRepresentation.Schema` `VersionIdentity` |
| Normalizer descriptor schema | `jax.provider_normalizer/v1` |
| Mapping/normalizer semantic version | descriptor `ComponentIdentity.Version` |
| Mapping implementation content | optional descriptor `ComponentIdentity.Content` |
| Canonical output schema | exact `ContractSchemaRef` |
| Canonical record revision | candidate/output `RevisionIdentity` |
| Canonical output bytes | `ContentIdentity(canonical_json)` |
| Provider adapter/API/build/configuration | existing independent identities, attached only when materially relevant |

A mapping change capable of changing canonical meaning requires a different component/version (and, where supplied, content) identity. Raw schema, mapping version, canonical schema, and build identity are never collapsed into one string.

## Timestamp, unit, enum, and identifier rules

- Provider timestamps are explicitly parsed by the provider adapter and converted to UTC. Parse failure, impossible order, or an ambiguous clock role fails; receipt time is never substituted for observation time.
- The proof converts an RFC3339 offset timestamp to the same UTC instant and preserves raw `ReceivedAt` as collection time.
- Unit mapping is a closed deterministic switch. Unknown units fail as unmappable; no default unit is inferred.
- Provider value-kind enum mapping is closed. `point` maps to canonical numeric observation, `range` is rejected as ambiguous, and unknown values are rejected as unmappable.
- Provider series/symbol identity is resolved to a canonical subject through a bounded resolver; it is never copied into a canonical ID or randomly converted.
- External/provider identifiers remain separate from typed canonical IDs.

## Quality-state boundary

The accepted envelope exposes only normalization quality `CANONICAL_VALIDATED`. Rejection is represented by a typed error and zero result. This is deterministic data-validation state, not WP-02.01 `CapabilityRuntimeState` health.

This package does not calculate freshness, TTL, staleness, last-known-good, fallback, retry, backoff, rate-limit state, provider health, trust, licensing score, cost, or preference.

## Failure taxonomy

`NormalizationError` carries stage, typed code, raw acquisition/provider/capability identity, bounded detail, and an unwrap-able cause. Its `Error()` never renders raw bytes or secrets.

Material codes cover:

- raw content verification and missing retrieval;
- unsupported provider, capability, raw schema, and representation/media;
- parser failure and missing required provider field;
- invalid, ambiguous, and unmappable provider values;
- identity resolution;
- canonical construction and canonical validation;
- provenance/linkage validation;
- unsupported target canonical version;
- exact normalizer version mismatch, unknown route, and ambiguous registration;
- inconsistent loss metadata;
- non-deterministic accepted output.

The parser/adapter returns stage-specific typed failures. An untyped adapter error is converted to a safe canonical-construction failure without exposing its text in the operator-visible error string.
