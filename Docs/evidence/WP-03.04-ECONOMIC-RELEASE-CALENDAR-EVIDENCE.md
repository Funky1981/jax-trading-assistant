# JAX HANDOVER — WP-03.04 ECONOMIC RELEASE / CALENDAR EVIDENCE

Status: **IMPLEMENTED — awaiting technical-lead review**

## Source selection

Implemented sources are the official FRED Web Services release endpoints and
the first-party U.S. Bureau of Labor Statistics iCalendar feed:

- FRED `/fred/releases` for broad release identity, press-release indicator,
  source link, and realtime metadata.
- FRED `/fred/releases/dates` for source-published release dates. The adapter
  makes `include_release_dates_with_no_data` explicit and preserves the
  resulting future/no-data distinction.
- BLS `https://www.bls.gov/schedule/news_release/bls.ics` for timestamped
  scheduled national-office releases.

The [FRED releases documentation](https://fred.stlouisfed.org/docs/api/fred/releases.html)
and [FRED release-dates documentation](https://fred.stlouisfed.org/docs/api/fred/releases_dates.html)
state that release dates are published by underlying data sources and do not
necessarily indicate FRED/ALFRED availability timing. BLS states that the
calendar is an upcoming-month schedule, is updated as needed, and uses Eastern
Time in its [schedule documentation](https://www.bls.gov/schedule/2026/07_sched.htm).

FRED `/fred/release`, `/fred/release/dates`, `/fred/release/series`, and
`/fred/series/release` were considered but are not required for this bounded
identity/date projection. BEA, Census, Treasury, EIA, Federal Reserve,
CBOE, and CFTC calendars remain WP-03.05 evaluation scope. HTML scraping was
not used because the BLS structured ICS feed satisfies the timestamped-source
requirement.

## Provider and contract

The provider-neutral package is `libs/releaseevidence`. Its
`EconomicRelease` contract preserves provider/source identity, source release
ID or UID, source name/description, optional authoritative reference-period
text, scheduled date, scheduled local time, IANA timezone, derived scheduled
UTC instant, optional end instant, optional actual-release instant, timing
authority, conservative status/data-availability, FRED realtime metadata,
source revision metadata, `AcquiredAt`, raw-payload references, and immutable
provenance.

`provider.CapabilityEconomicCalendar` is the single capability
`macro.release_calendar`. FRED (`pvd_fred`) and BLS (`pvd_bls`) both advertise
the versioned provider-neutral output `jax.releaseevidence/economic_release/v1`.
The contract contains no FRED DTO, BLS structure, or iCalendar library object;
another official calendar adapter can emit the same representation.

The legacy `libs/calendar` package was inspected and was not reused: it
represents scheduled time as a single timestamp, includes actual/forecast
fields, and owns a separate file store, which would violate this package's
temporal and raw-evidence boundary.

## Temporal semantics

`Date` is a date-only value and is never converted to midnight UTC. A FRED
release date therefore has `TimingAuthority=DATE_ONLY_SCHEDULE`, no local time,
no timezone, no scheduled instant, and no actual-release instant.

BLS local date-times are normalized with IANA timezone rules. The official
Eastern-Time meaning is mapped to `America/New_York`; no machine-local or
year-round UTC-5 assumption is used. `TimingAuthority=SCHEDULED_LOCAL_TIME`
means the scheduled local time is authoritative and the UTC instant is derived
with DST rules. It does not mean the release was actually public at that
instant.

`DTSTART` is the scheduled event time. `DTSTAMP` and `LAST-MODIFIED` are kept as
source calendar metadata in `SourceRevision`; neither is used as a release or
publication time. An `ActualReleaseInstant` is not fabricated and can only be
valid with `ACTUAL_RELEASE_TIME` authority.

FRED realtime start/end dates, BLS source metadata timestamps, economic
reference-period text, scheduled time, actual availability, and Jax
`AcquiredAt` remain separate. No observations, revisions/vintages, forecasts,
consensus, surprise, market reaction, signals, or trading events are ingested.

## Raw evidence and operations

Both adapters use the Phase 02 `OperationalExecutor`, exact entity-body
capture, shared `provider.RawPayloadStore`, SHA-256/read-back verification,
deterministic parsing, and provenance built from immutable raw evidence refs.
Parsing occurs only after persistence. FRED metadata and date pages are
separate raw payloads; BLS is one exact `text/calendar` response. Request
credentials never enter payload metadata, provenance, errors, or logs; the
BLS public feed adds no authentication.

FRED pagination validates count, offset, limit, requested ordering, page
progression, duplicate release IDs/occurrences, and cross-page consistency.
Any malformed or partial sequence is returned `INCOMPLETE`/error rather than
being treated as complete. BLS is reported as complete for the returned feed
only; it is not an exhaustive historical BLS archive.

The source feed itself is bounded/upcoming. A recent download does not make a
historical schedule economically fresh, and the package does not fabricate a
historical first-known/market-knowability timestamp. Historical schedule
entries acquired later establish source schedule evidence, not the exact date
on which that schedule first became publicly knowable. Calendar freshness is
therefore an explicit future operational policy concern, separate from macro
value freshness.

## Revisions and cross-source identity

FRED release identity uses the authoritative release ID plus the date
occurrence. BLS identity uses the authoritative UID, scheduled date, and
source revision components where supplied (`SEQUENCE` and `LAST-MODIFIED`). A
later acquisition with the same UID and a changed schedule produces a distinct
normalized identity while the earlier raw acquisition remains retrievable.
No title similarity or fuzzy cross-source matching is used. FRED and BLS
records remain separate even when their human-readable names appear related.

## Qualification and freshness

The qualification framework remains source/capability scoped rather than a
generic trust score. BLS is first-party authoritative for its own scheduled
release calendar. FRED is an official St. Louis Fed distribution platform
conveying release dates published by underlying source agencies; it is not
asserted to be the original publisher of every release. Access, coverage,
timing, update, and source-history limitations above remain part of the
qualification evidence. No universal qualification `GO` is asserted here.

## Dependency

The BLS parser uses `github.com/arran4/golang-ical` v0.3.6, an Apache-2.0
licensed maintained RFC 5545 parser. Raw ICS bytes are retained before the
library is invoked and library types do not cross the provider-neutral
boundary. No new database migration or normalized calendar table was needed;
durable PostgreSQL-compatible raw storage already exists in Phase 02.

## Verification

Deterministic tests cover date-only FRED semantics, FRED future/no-data mode,
realtime metadata, API-key exclusion, exact raw bytes, pagination failure,
BLS multiple events, UID, date-only DTSTART, scheduled local time, timezone
aliases, standard/DST conversion, DTSTAMP/LAST-MODIFIED separation, cancelled
status, malformed/duplicate/invalid-timezone failures, provider neutrality,
and rescheduling across distinct raw acquisitions. Live BLS and FRED
verification were **NOT PERFORMED**; no approved FRED API key was configured.

Trading/execution safety was not changed. Hosted model inference was not used.
WP-03.05 was not started.

Known limitations are the bounded BLS feed coverage, FRED date-only release
timing, absent historical schedule first-known semantics, absence of an
authoritative actual-publication timestamp in these selected feeds, and no
broader cross-source reconciliation. These are intentional WP-03.04
boundaries; further official-source evaluation belongs to WP-03.05.
