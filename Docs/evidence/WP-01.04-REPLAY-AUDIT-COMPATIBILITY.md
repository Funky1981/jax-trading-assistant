## AuditEvent design and semantics

`jax.audit_event/v1` is the smallest canonical record that answers what Jax did and what immutable material it acted upon.

| Field/concept | Semantics |
| --- | --- |
| `aud_` ID | Unique historical event identity. |
| `ast_` stream plus positive sequence | Total order only inside one logical history stream. No global sequence is implied. |
| `adi_` idempotency identity | Future writers must reject a repeated logical append independently from event ID. |
| action | Closed set: record created/superseded, processing completed/failed, compatibility assessed/applied. |
| subject | Typed domain-record identity. It cannot identify an `AuditEvent` or masquerade as canonical domain `Event`. |
| inputs/fingerprint | Ordered WP-01.03 immutable lineage references plus a recomputed SHA-256 fingerprint. |
| output/supersedes | Exact immutable canonical record revisions. A supersession retains both old and replacement identities. |
| producer/components/provenance | Exact versioned component identities and the accepted `pvn_` lineage identity. |
| compatibility | Optional typed compatibility assessment; required for compatibility actions. |
| outcome/failure | `SUCCEEDED`, `FAILED`, or `REJECTED`; failure history uses a closed code and `fail_` identity. |
| correlation/causation | Groups one processing path and optionally links to an earlier audit cause without embedding it. |
| knowledge/occurred/recorded clocks | `knowledge_cutoff` states the point-in-time input boundary; `occurred_at` is when Jax action happened; `recorded_at` is when history was recorded. |

Successful creation/completion cannot omit immutable input, provenance, or output. Failed processing cannot claim an output. Unsupported attempted schema versions are permitted as audit subjects only when the event fails explicitly with `unsupported_contract_version`.

## Immutable history policy

Historical canonical domain revisions, `AuditEvent`s, replay manifests, and their content identities are immutable. Correction never overwrites an earlier historical meaning:

```text
immutable revision N --record_superseded--> immutable revision N+1
          |                                      |
          +--------------- both retained --------+
```

A retracted, deleted, corrected, or disputed upstream fact produces a later canonical Event/Evidence revision and audit history that supersedes the prior revision. The bytes and knowledge cutoff used by the historical output remain available and verifiable. A reviewer can therefore distinguish what Jax knew then from a later source state.

`AuditEvent` stores old/new immutable references rather than a hand-authored change payload. What changed is derived deterministically by comparing the two verified canonical records, so the audit record cannot drift from the content it describes.

The contract does not demand repository-wide event sourcing. Current operational tables can continue to store application state. Adoption requires an owner-specific adapter that writes immutable history reliably before claiming reconstructability.

## Current projection policy

A current projection is a mutable read model derived from immutable history. It may select the latest non-retracted revision or current decision, but it is never the forensic source of truth.

Every future projection adopting this model must retain:

- the exact immutable output reference from which it was derived;
- the last applied `AuditEventRef` and stream sequence;
- the projection/version identity used to derive the current representation.

Rebuilding a projection means replaying validated history in per-stream sequence order. Projection deletion or replacement does not delete history. Existing `genuine_event_decisions.is_current` plus retained decision versions is the closest active Jax example; the mutable evidence-subject row and latest frontend joins are projections, not complete history.

## Ordering, causation, and idempotency

- `(stream_id, sequence)` is the ordering authority. Sequence starts at 1 for a complete stream and is contiguous.
- Wall-clock timestamps do not establish total order and ties are valid.
- `ValidateAuditTrail` rejects duplicate event IDs, duplicate idempotency IDs, stream gaps/reordering, and causation that does not point to an earlier supplied event.
- Future persistence must enforce uniqueness for event ID, idempotency ID, and `(stream_id, sequence)` transactionally.
- There is no global sequence, consensus protocol, previous-event hash, or hash chain.

A hash chain was rejected because exact canonical content digests, contiguous stream sequence, and immutable references provide the required Phase 01 verification without imposing cross-stream coordination or blockchain-like storage. A later tamper-evident store may add a separately versioned chain policy without changing V1 event bytes.

## Failure history

Material failures are history, not successful events with warning text. Closed failure codes cover validation rejection, unsupported versions, provenance mismatch, missing immutable input, component/model-provider failure, unavailable compatibility translation, digest mismatch, and non-reproducible replay.

Canonical failure detail is bounded diagnostic text. It must not contain credentials, tokens, raw evidence/provider payloads, prompts/responses, or stack traces. Exact failed input bytes remain separately content-addressed when available.

## ReplayManifest design

`jax.replay_manifest/v1` identifies one target historical domain output and everything required to verify its reconstruction:

- exact target record/revision/content digest;
- ordered immutable Evidence/contract/dataset inputs and recomputed input fingerprint;
- original producer and all materially relevant model/prompt/policy/tool/build/configuration identities;
- the subset of component identities actually required for this replay strategy;
- ordered immutable `AuditEventRef`s for the historical processing path;
- stored immutable model-response Evidence refs when historical AI output was involved;
- explicit compatibility assessments, if migration is used;
- replay claim, strategy, failure reason when unavailable, and creation time.

Machine-local file paths are absent. Dataset identity uses the accepted logical dataset/snapshot/revision/content model. `ReplayMaterials` is a non-canonical in-memory verification input for fixtures and future adapters; it is not a storage or service API.

`VerifyReplayManifest` validates every reference, recomputes hashes, verifies the target canonical bytes, verifies required component identity/content, validates the referenced audit trail, and fails with `ReplayVerificationError` codes. It performs no provider/database/model call.

## Replay claims

| Claim | Meaning | What it does not mean |
| --- | --- | --- |
| `EXACT` | The target canonical bytes match and all recorded immutable inputs plus required component identities/content are available. Strategy is deterministic re-execution or immutable-history reconstruction. | A semantically similar newer answer, an implicit schema upgrade, or model re-inference. |
| `COMPATIBLE_MIGRATED` | A different supported schema is reached through explicit validated lossless/lossy translation declarations whose adapter identities are required replay components. | Byte-identical historical replay. Lossy translation remains visibly lossy. |
| `UNAVAILABLE_NON_REPRODUCIBLE` | A required immutable input/version/component/response is unavailable or invalid; the manifest carries an explicit typed reason and verification fails. | Best-effort success or silent fallback. |

An exact claim with a required model component is invalid because that would require stochastic re-inference. Exact reconstruction may record a model identity as historical context only when the immutable original model response is preserved as Evidence V2 and the model is not required to run again.

## Contract compatibility strategy

`ContractSchemaRef` identifies a supported domain family/version. `ContractCompatibility` classifies one explicit source/target pair:

| Classification | Rule |
| --- | --- |
| `EXACT` | Same kind and same schema version; no adapter, loss, or reason. |
| `LOSSLESS_TRANSLATION` | Different versions of the same family; a versioned `mapping` component with exact content identity is mandatory; no loss entries. |
| `LOSSY_TRANSLATION` | Different versions of the same family; the exact mapping component and one or more typed information-loss entries are mandatory. |
| `INCOMPATIBLE` | No translation exists; no translator may be supplied and a reason code is mandatory. |

`ResolveContractCompatibility` automatically returns exact only for identical supported schemas. Every version change requires exactly one validated declaration. Missing, ambiguous, invalid, cross-family, and future/unsupported translations fail closed. Translation execution is deliberately not implemented in WP-01.04.

### V1 to V2 reality

Evidence, Observation, ResearchRun, QuantResult, and Recommendation V1 records do not contain the immutable provenance required by accepted V2. `V1ToV2WithoutHistoricalProvenance` therefore returns `INCOMPATIBLE / insufficient_historical_provenance`. It never invents a hash, source, provider, revision, lineage, or component identity.

A future adapter can declare lossless or lossy V1-to-V2 translation only when separately retained historical bytes and identities genuinely supply the V2 requirements. The adapter's mapping version and exact mapping content must be recorded. The original V1 record remains immutable.

## Normative `jax.canonical-contract-json/v1` byte specification

This section is normative and is independent of Go implementation behavior. It preserves the WP-01.03 encoding and does not introduce a second format.

### Envelope and character encoding

The byte sequence is exactly one compact UTF-8 JSON object, with no BOM, leading/trailing whitespace, or final newline:

```json
{"canonicalization":"jax.canonical-contract-json/v1","contract_kind":"<kind>","contract_version":"<schema>","content":<canonical-record>}
```

Envelope property order is exactly `canonicalization`, `contract_kind`, `contract_version`, `content`. The envelope kind/version must equal the validated content type/version.

All strings must be valid UTF-8. Unicode scalar values are preserved without normalization. `"`, `\\`, backspace, form feed, newline, carriage return, and tab use `\"`, `\\`, `\b`, `\f`, `\n`, `\r`, and `\t`. Other U+0000-U+001F characters use lower-case `\u00xx`. `<`, `>`, and `&` use `\u003c`, `\u003e`, and `\u0026`; U+2028 and U+2029 use lower-case `\u2028` and `\u2029`. `/` is not escaped. Other scalar values are emitted directly as UTF-8.

### Objects, omission, null, booleans, and arrays

- Object properties use the fixed schema order below. They are never lexically sorted.
- A property tagged optional is omitted when its string is empty, pointer is absent, or array length is zero. Omission does not leave a placeholder.
- Canonical output never contains JSON `null`; canonical decode rejects explicit `null` at any depth.
- Duplicate property names, unknown fields, trailing data/values, invalid UTF-8, and unsupported versions are prohibited.
- Booleans are exactly `true` or `false`.
- Array order is semantic and preserved exactly. No canonical encoder sorts or deduplicates arrays. Validation rejects duplicates where the contract declares uniqueness.
- Canonical contract types contain no maps.

### Numbers and time

- Integers use base-10 digits with no leading plus or unnecessary leading zero.
- Floating values are finite IEEE-754 binary64 values using the shortest base-10 representation that round-trips to the same binary64 value. Fixed notation is used for absolute values in `[1e-6,1e21)` and exponent notation outside that range; exponent `e` is lower-case and exponent leading zeros are removed. Negative zero, NaN, and infinities are prohibited.
- Times are quoted UTC RFC 3339 Nano values with `Z`, a four-digit year, and `YYYY-MM-DDTHH:MM:SS`. A fractional second is omitted when zero; otherwise 1-9 digits are emitted with trailing zeros removed. Non-zero offsets are prohibited.

## Representative reconstruction proof

`TestRepresentativeHistoricalOutputReconstruction` builds a fixed, in-memory chain with no database, logger, provider, model, candidate, approval, paper ticket, execution instruction, order, trade, or fill:

```text
exact SEC-like raw bytes + source/provider/revision/times
                         |
                    Evidence V2
                         |
                   Observation V2
                         |
                   ResearchRun V2
                         |
                    QuantResult V2
                         |
                  Recommendation V2
                         |
        five ordered immutable AuditEvent records
                         |
              exact ReplayManifest verification
```

The proof verifies source and provider separately, all V2 versions, every canonical content digest, ordered input fingerprints, run/result/recommendation provenance, producer/component versions, audit correlation/causation/stream sequence, knowledge timestamps, the target Recommendation bytes, and research-only authority `NONE`. Reconstruction consumes only supplied immutable material and does not inspect logs.

Negative tests remove inputs and the historical AI response, alter exact provider bytes, alter a canonical Recommendation, change a required component version, corrupt fingerprints, repeat event/idempotency identity, break sequence, self-cause, use invalid/unsupported versions, omit producer identity, and attempt undeclared/lossy-as-exact compatibility. All fail explicitly.

## Exact replay limitations

- Existing Jax mechanisms are not automatically compliant; only the in-memory canonical proof is exact today.
- A content digest proves bytes, not external truth. Assertion/dispute/retraction remains domain state and later history.
- `EXACT` does not promise bit-for-bit floating-point behavior across arbitrary future hardware unless the relevant algorithm/build/config identity and deterministic numeric contract are retained.
- Historical model output can be reconstructed exactly only from its stored immutable response. Re-running a hosted/local stochastic model is never exact under V1.
- A compatibility migration can be deterministic and still not be byte-identical. Lossy migration stays visibly lossy.
- Stream integrity assumes an adopting persistence layer enforces append/uniqueness transactionally. No such persistence is added here.

## Deferred adoption and migration

- No database migration or audit table is required for Phase 01.
- Future owner packages must define reliable append transaction boundaries and projection checkpoints before claiming complete history.
- Existing artifact, dataset, event-decision, evidence-subject, AI-shadow, candidate, macro, paper-outcome, orchestration, and legacy execution systems require separate reviewed adapters/migration decisions.
- Production historical replay/orchestration belongs to Phase 07; workflow audit belongs to Phase 10. This package does not start either phase.
- No V3 schema, event bus, event-sourcing framework, or third-party replay library was introduced. Standard Go JSON/SHA-256 plus the accepted Jax contracts are sufficient for this bounded foundation.
