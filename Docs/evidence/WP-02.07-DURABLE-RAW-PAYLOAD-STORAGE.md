# WP-02.07 — Durable Raw Payload Storage & Runtime Composition

Status: implemented in the `capability-reset` runtime at the WP-02.07 starting
HEAD. WP-03.02 is not started.

## Architecture

Jax uses the existing PostgreSQL runtime as one provider-neutral
`RawPayloadStore` implementation in `internal/rawpayloadstore`. The accepted
contract in `libs/contracts/provider` remains the owning interface.

Migration `000055_raw_payload_storage` creates two append-only tables:

- `raw_payload_contents` has one row per SHA-256 digest and stores the exact
  bytes in PostgreSQL `BYTEA`, the raw-bytes representation, digest algorithm,
  byte count, and creation time.
- `raw_payload_acquisitions` has one row per `rpa_...` acquisition identity,
  references the content digest, stores typed contract-critical fields, and
  keeps a validated complete `RawPayloadRef` JSON snapshot for lossless
  reconstruction of the current contract.

The acquisition row is deliberately not content identity. Identical bytes
from different acquisitions share one content row and retain separate
acquisition records.

The database protects both tables with append-only triggers. The application
adapter exposes only `Put` and `Get`; it has no update, replacement, rebinding,
or deletion API. Retention and redistribution metadata are persisted, but no
GC, TTL, legal-hold, or deletion workflow is implemented.

## Put and Get guarantees

`Put` validates the reference and supplied bytes before opening a transaction.
Inside one transaction it inserts or locks the digest row, reads the stored
content back, verifies byte count, SHA-256, representation, and exact byte
equality, then inserts the acquisition with `ON CONFLICT DO NOTHING`. The
acquisition is read back and compared using the complete encoded immutable
reference before commit.

The same acquisition and identical immutable meaning is idempotent. Reusing
an acquisition ID with changed bytes, digest, provider, capability, source,
revision, capture, receipt, size, retention, or other reference meaning fails
with `duplicate_identity_conflict`; it never overwrites evidence. A content
digest conflict is read and verified rather than trusted from the conflict
clause.

`Get` joins the acquisition and content rows, decodes and validates the stored
reference, requires it to match the supplied typed reference, verifies the
stored content identity, size, and digest, and returns a defensive copy.
Missing, malformed, inconsistent, truncated, or tampered records fail closed.

The logical location is:

```text
store: jax.raw_payload_store/postgres/v1
key:   sha256/<lowercase-sha256>
```

It contains no SQL row ID, DSN, connection detail, credential, filesystem
path, URL, or bucket name. A future filesystem/object-store adapter can use a
different physical placement without changing `RawPayloadRef` identity.

## Failure and restart model

The transaction makes content and acquisition publication atomic from the
application's perspective. A crash or failed verification before commit rolls
back both rows. A concurrent same-digest insert is serialized by the digest
primary key and then read/verified. A concurrent same-acquisition insert is
serialized by the acquisition primary key and then compared; one immutable
meaning wins and a conflicting meaning fails. A content row created in a
transaction whose acquisition publication fails is rolled back, so the
PostgreSQL implementation does not intentionally create orphan content.

The outer Phase 02 `PersistRawPayload` flow still performs its required
post-`Put` `Get`, size, digest, and exact-byte verification before publishing a
descriptor.

## Runtime composition

After the existing trader PostgreSQL pool is created and pinged, `main` creates
one `PostgresRawPayloadStore`. That same interface instance is passed into the
trader market-tool composition and the compatible frontend market-tool
composition. Existing legacy market-data consumers are unchanged. The
hardened Financial Datasets API already accepts `FinancialDatasetsBarsDependencies.Store`;
the shared durable instance is now available at the runtime boundary for that
path and for later SEC, FRED/ALFRED, Treasury, EIA, CBOE, and CFTC adapters.

There is no production fallback to `MemoryRawPayloadStore`. A future evidence
acquisition caller must pass the composed store; a nil or unavailable store is
rejected by the accepted persistence contract. The current trader process does
not invent a provider execution path for the hardened Financial Datasets
method, and its legacy candle path remains outside this package's scope.

## Security boundary

Only successful provider entity-body bytes reach the store. The current
Financial Datasets hardened adapter captures exact response bytes and sends
`X-API-KEY` only on the request. Authentication headers, API keys, cookies,
signed request material, and secret configuration are not fields of
`RawPayloadRef` and are not persisted. Raw content is not written to ordinary
errors or logs. Entity bodies may themselves contain sensitive source data;
database access control/encryption remains operational hardening outside this
package.

## Size, replay, and qualification boundaries

The `[]byte` contract and provider capture boundaries target bounded individual
responses. The Financial Datasets hardened path currently caps one response at
4 MiB. No SEC bulk archive or general large-object policy was added. Very large
filing files and bulk archives require a future explicit provider/package
review and must not silently enter this store.

`RawPayloadRef` remains available to the accepted normalization/replay flow.
`canonical.EvidenceRef` was not changed and does not directly retain
`RawPayloadID`; acquisition-level replay linkage therefore remains a separate
contract decision. Durable storage does not change provider qualification,
licensing, redistribution, or paper-only execution policy.

## Verification

The migration declaration test checks the two-table split, `BYTEA`, foreign
key, reference snapshot, append-only trigger, and rollback declarations. The
PostgreSQL integration test is enabled only with
`JAX_RAW_PAYLOAD_TEST_DATABASE_URL`; it runs migrations and checks exact binary
round-trip, defensive copies, idempotency, restart-style reconstruction,
same-content deduplication, acquisition conflict, and missing retrieval.

The integration test intentionally does not weaken append-only protections to
manufacture database corruption. Corruption testing should use a dedicated
database-admin/test-fixture policy if required later.
